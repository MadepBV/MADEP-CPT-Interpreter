# Audit — Retaining/sheet-pile walls — geometry & beam coupling
**Subsystem key:** walls
**Files reviewed:** src/lib/cpt-app/wall-geometry.js, src/lib/cpt-app/stage6-bishop.js (wall sections: 560-960, 1035-1132, 1257-1399, 2320-2428, 2870-2959), src/lib/cpt-app/deformation/mesh.js (wall sections: 263-630), src/lib/cpt-app/deformation/solver.js (6340-6574, 2227), src/lib/cpt-app/seepage/solver.js (300-349), src/lib/cpt-app/seepage/boundary.js (210-246), src/lib/cpt-app/seepage/drains.js (refs), src/lib/cpt-app/legacy-controller.js (wall refs: 5552-5602, 7435-7585, 11790-11829, 12209), docs/bishop/retaining_walls_extension_spec.md, src/routes/docs/engineering/beam/+page.svelte
**Finding counts:** critical=0 high=2 medium=5 low=4 info=3  |  A=4 B=1 C=4 D=4  |  total=14

## Overview
The wall-geometry helper module (`wall-geometry.js`) is small, clean, and numerically sound: the two-point head→tip axis, orthonormal normals, station projection, point/segment distance, oriented rectangle, segment/segment intersection, and circle/segment intersection are all mathematically correct, and the "legacy vertical wall" convention (t=(0,−1) ⇒ nRight=+x) is preserved exactly as documented in the source comment. The risks in this subsystem are mostly at the *coupling* layer (stage6-bishop.js and mesh.js), not in the geometry primitives: an inclined wall computes passive resistance from a strictly *vertical* soil column at a single probe x and treats the resultant as purely horizontal (a documented but unverified simplification that the doc explicitly disclaims for inclined walls), the Spencer interslice wall force is added with a fixed +x sign regardless of `passiveSide`, and there is a latent `mechanicalActive` default mismatch (default-OFF everywhere except mesh.js, which is default-ON). The paired doc `retaining_walls_extension_spec.md` describes a *vertical-wall-only* v1 and is now partly out of date with the shipped two-point/inclined geometry and the per-segment multi-layer passive integration; the beam in-app doc page contains no wall content and is not a meaningful cross-reference for this subsystem. No confirmed critical correctness defect was found in the geometry primitives themselves.

## Findings

### [WALLS-A-01] high · Inclined wall: passive resistance integrated over a vertical soil column and applied as a purely horizontal force
- **Location:** `src/lib/cpt-app/stage6-bishop.js:770-804` (passive integration), `:805,820` (`passiveNormal` computed but unused for direction), `:803-804` (horizontal-only moment arm); geometry support `src/lib/cpt-app/wall-geometry.js:32-53` (inclined axis/normals)
- **Category:** A — Implementation
- **Confidence:** confirmed (math), likely (engineering severity)
- **Analysis:** `computeWallIntersections` builds the passive resistance from `wallPassiveSegments`, which probes a **vertical** region stack at a single x (`xProbe`) and integrates `σ_p(z)=Kp·γ·z + 2c√Kp` over depth-below-terrain `z1=terrainSurfaceY−yTop`, `z2=terrainSurfaceY−yBottom`. The force is then `0.5·Kp·γ·(z2²−z1²)+2c√Kp·(z2−z1)` and the resultant `R_passive` is treated as **horizontal**: `momentArm = circle.center.y − y_application` (vertical lever only) and, in Spencer, `ELeft += wallForceLeft` (horizontal). For a genuinely inclined wall (head.x ≠ tip.x, per the two-point geometry added in the recent commits), this is physically inconsistent in three ways: (1) the embedded resisting length is the *inclined* segment length `axis.length − station`, not the vertical depth interval `z2−z1`; integrating Rankine pressure over vertical depth understates/overstates the soil column depending on inclination; (2) the passive resultant on an inclined wall acts **normal to the wall face** (direction `passiveNormal`, which is computed at :805 and stored at :820 but never used to resolve the force — only the magnitude `R_wall` enters equilibrium); (3) `wallPassiveProbePoint` probes one fixed x offset normal to the wall, but the column is then integrated vertically through `probeVerticalRegionStack`, mixing an inclined probe location with a vertical integration path. The geometry helpers themselves are correct; the defect is that the *physics layer* assumes verticality. The paired doc explicitly lists "Inclined walls: only vertical walls … would require modifying the intersection geometry and the force direction" as a v1 non-feature (spec §13.3), so the code now ships geometry the spec says was not supposed to be force-modelled.
- **Recommendation:** For inclined walls, integrate passive pressure over the inclined embedded length and resolve the resultant along `passiveNormal` (decompose into horizontal/vertical components for the moment about the centre and for the Spencer chain), or explicitly gate the passive-force path to near-vertical walls and document the restriction. At minimum, surface a warning when `|head.x − tip.x|` is non-negligible so users are not given a plausible-but-wrong inclined-wall FS.

### [WALLS-A-02] high · Spencer interslice wall force added with fixed +x sign, ignoring `passiveSide`
- **Location:** `src/lib/cpt-app/stage6-bishop.js:1289` (`ELeft += Number(slice?.wallForceLeft) || 0;`), `:838` (`wallForceLeft` summed as `+R_wall`, no sign), `:805,820` (`passiveNormal` available but unused)
- **Category:** A — Implementation
- **Confidence:** likely
- **Analysis:** Spencer force equilibrium propagates the interslice normal force `ELeft` left→right across slices sorted by ascending x. At the slice whose left edge is the wall, the code does `ELeft += wallForceLeft`, where `wallForceLeft = Σ R_wall` is always positive (line 838). This is correct only when the wall's passive resistance pushes in the +x direction, i.e. `passiveSide === 'right'` (which is exactly the orientation the doc §7.2 assumes: "the wall pushes the passive-side slices"). The model does **not** normalise slide direction to a fixed orientation — `moveSign = sign(exit.x − entry.x)` can be ±1 (stage6-bishop.js:435, 2442) — and walls carry an explicit `passiveSide` that can be `'left'`. For a `passiveSide:'left'` wall (resistance acting in −x), the interslice force should be `ELeft −= R_wall`, but the code unconditionally adds `+R_wall`. The Bishop *moment* term is sign-agnostic (always treated as resisting, divided into the driving denominator), so this only mis-signs the Spencer **force** chain, but Spencer is the converged result reported to the user. Note this is consistent with the doc's stated vertical/right-passive simplification, so it is a real limitation rather than a clear contradiction of the spec; severity depends on whether left-passive walls are reachable from the UI (`passiveSide` is user-settable per legacy-controller.js:8905, 11804).
- **Recommendation:** Resolve the wall force sign from `passiveSide` (or from `passiveNormal.x`) before adding to `ELeft`: `ELeft += Math.sign(passiveNormal.x) * R_wall` (or `passiveSide==='left' ? −R_wall : +R_wall`). Add a regression test with a `passiveSide:'left'` wall and confirm FS increases (not decreases).

### [WALLS-A-03] medium · Bishop wall moment is always stabilising regardless of whether the wall lies on the driving or resisting side
- **Location:** `src/lib/cpt-app/stage6-bishop.js:803-804` (`M_wall = R_wall·(yc − y_app)`), `:2346-2347` (`driving -= wallMomentTerm`), `:821` (`momentTerm = M_wall/R`)
- **Category:** A — Implementation
- **Confidence:** likely
- **Analysis:** The wall moment term is computed as `R_wall·(yc − y_application)/R` and unconditionally **subtracted** from the driving denominator (and, when it exceeds driving, the surface is reported "stable by wall alone", :2353). Because `y_application` is always below the centre `yc` for an embedded wall, `(yc − y_app) > 0`, so the term is always positive and always increases FS. This assumes the wall is always on the resisting side of the slip mass. For a circle whose geometry places the wall in the *driving* zone (e.g. a deep circle that intersects the wall high up where the soil above is part of the sliding wedge), a real passive mobilisation would not be available / would not resist sliding, yet the code still credits a full passive resisting moment. The doc (§3, §4) implicitly assumes the wall separates an active (driving) side from a passive (resisting) side and the engineer places it accordingly, so this is a modelling simplification, but there is no guard that the credited passive resistance is kinematically admissible for the given circle. Compare to the geometry classification (passedBelow/passedAbove) which only filters out non-intersecting cases — it does not check driving-vs-resisting side membership.
- **Recommendation:** Verify, using the slide direction (`moveSign`) and the wall's `passiveSide`, that the passive side is the down-slope/resisting side for each intersecting circle; if the intersection puts the passive zone on the driving side, drop the wall credit for that surface. Document the assumption either way.

### [WALLS-A-04] medium · `mechanicalActive` default mismatch: default-OFF everywhere except deformation mesh builder (default-ON)
- **Location:** `src/lib/cpt-app/deformation/mesh.js:291-292` (`wall?.mechanicalActive !== false` → default ON) vs `src/lib/cpt-app/stage6-bishop.js:2913` (`=== true` → default OFF), `src/lib/cpt-app/deformation/solver.js:2227` (`=== true`), `src/lib/cpt-app/legacy-controller.js:5553,7736,8325` (`=== true`)
- **Category:** A — Implementation
- **Confidence:** likely
- **Analysis:** Every gate in the codebase treats `mechanicalActive` as **default OFF** (an explicit `=== true` test): the model normaliser (legacy-controller.js:5553 sets it to a strict boolean), the deformation "has mechanical?" gate (`solver.js:2227 some(wall => wall?.mechanicalActive === true)`), and the Bishop model builder (stage6-bishop.js:2913 `mechanicalActive: wall?.mechanicalActive === true`). The lone exception is the mesh builder `activeMechanicalWalls` (mesh.js:292), which uses `wall?.mechanicalActive !== false` — i.e. **default ON**, with an inline comment ("Treat missing/undefined as ON"). In the production pipeline this is masked because the model reaching `buildDeformationMesh` always passes through `buildBishopModelFromStageLayers` (solver.js:6342 `input.model`), which sets `mechanicalActive` to a strict boolean. But the gate semantics are contradictory: if a wall ever reaches mesh.js with `mechanicalActive: undefined` (a direct `buildDeformationMesh` caller, a test, or a future refactor), `hasMechanicalDeformation` (solver.js:2227) would say "no walls" while the mesh builder would still embed beam DOFs — an inconsistent state. The comment's appeal to "Spec principle #11: walls participate automatically" also contradicts the rest of the code's default-OFF behaviour.
- **Recommendation:** Make mesh.js:292 match the rest of the codebase: `.filter(({ wall }) => wall?.mechanicalActive === true)`. If the intended behaviour really is default-ON, change it everywhere (and the UI) — but pick one definition.

### [WALLS-B-01] medium · O(intersections × slices) wall-to-slice tagging on the hot search path
- **Location:** `src/lib/cpt-app/stage6-bishop.js:829-848` (`applyWallInteractionsToSlices`), `:771-775` (per-slice `wallForceAtSlice` map rebuild pattern mirrored in Spencer), and the per-wall `.filter(...).filter(...)` chains in `computeWallIntersections:735-741`
- **Category:** B — Performance
- **Confidence:** confirmed
- **Analysis:** `applyWallInteractionsToSlices` runs `slices.map(slice => wallIntersections.filter(... |slice.xL−item.x|<=1e-6 ...))` — for every slice it linearly scans all wall intersections, and does so twice (leftWalls and rightWalls), allocating two filtered arrays + a `.map` + two `.reduce` per slice. This is O(nSlices × nWalls) per trial circle, and the whole thing runs inside the grid/radius search loop that evaluates thousands of circles. For typical inputs (few walls, ~30 slices) the constant is small, but the per-circle allocation churn (fresh arrays, fresh objects via `{...slice}`, `wallInteractionsLeft.map`) on a tight search loop is wasted work and GC pressure. The float-equality tag `Math.abs(slice.xL − item.x) <= 1e-6` is also fragile: the slice break is `hit.point.x` and the tag compares against the same `hit.point.x`, so it matches today, but any independent rounding (e.g. the `+s.toFixed(6)` style rounding used in mesh.js) would silently drop the tag and lose the wall force entirely.
- **Recommendation:** Build a `Map<xKey, R_wall_sum>` once per circle (key = rounded x) and look up by slice edge, instead of nested filters; or attach the wall directly when the slice break is created. Avoid per-slice array allocation when `wallIntersections.length === 0` (already partially short-circuited, but the `.map` still clones every slice).

### [WALLS-C-01] medium · Doc still specifies a vertical-only wall (`x`, `yTop`, `yTip`); code ships a two-point head→tip inclined wall
- **Location:** Doc `docs/bishop/retaining_walls_extension_spec.md:108-130` (struct `RetainingWall { x, yTop, yTip }`), §4.2 "Intersection of circle with vertical line x = x_wall", §13.3 "Inclined walls: only vertical walls". Code `src/lib/cpt-app/wall-geometry.js:14-53` (head/tip endpoints, inclined axis), `src/lib/cpt-app/stage6-bishop.js:2894-2932` (head/tip wall model, falls back to x/yTop/yTip)
- **Category:** C — Doc vs code
- **Confidence:** confirmed
- **Analysis:** (1) The doc defines a wall purely by `x` + `yTop` + `yTip` and computes the slip intersection against the **vertical line** `x = x_wall` (`y_intersect = yc − sqrt(R² − (x_wall − xc)²)`, §4.2). (2) The code defines a wall by two arbitrary points `head`/`tip` (`wallEndpoints`, `wallAxis`) and intersects the slip circle with the **inclined segment** (`circleWallSegmentIntersections`, wall-geometry.js:122-142). The legacy `x/yTop/yTip` form is retained only as a fallback (wall-geometry.js:15-22, stage6-bishop.js:2897-2904). (3) Scientifically the code's two-point model is the more general/correct geometry; for a vertical wall it reduces exactly to the doc's formula (axis t=(0,−1)), so the code is a strict superset. (4) Fix direction: update the doc — `RetainingWall` should be documented as `{ head:{x,y}, tip:{x,y}, … }` with the vertical case as a special case, the §4.2 intersection rewritten as circle∩segment, and §13.3 "inclined walls not supported" removed or revised to reflect partial support (with the caveat in WALLS-A-01).
- **Recommendation:** Fix the doc to match the shipped two-point geometry; carry forward the WALLS-A-01 caveat that the *force* model is still effectively vertical.

### [WALLS-C-02] medium · Doc passive integration is single-layer / triangular-1/3; code does per-segment multi-layer integration with a true centroid
- **Location:** Doc §5.1 (`R_passive = 0.5·Kp·γ·(z_tip²−z_int²) + 2c√Kp·d`) and §5.4 (`y_application = yTip + d/3`, "1/3 above tip … simplification"). Code `src/lib/cpt-app/stage6-bishop.js:773-802` (per-segment loop, water-aware γ, true first-moment centroid `y_application = yMoment/R_passive`)
- **Category:** C — Doc vs code
- **Confidence:** confirmed
- **Analysis:** The doc presents the single-layer closed form and the simplified 1/3-depth point of application (explicitly calling it a "Practical simplification … slightly conservative"). The code is more rigorous: it walks a layered region/band stack (`probeVerticalRegionStack` / `wallPassiveSegmentsLegacy`), applies layer-specific `Kp`, `c'`, and γ (dry vs saturated by phreatic level), sums forces, and computes the *exact* pressure-distribution centroid via `firstMoment = terrainSurfaceY·force − a/3·(z2³−z1³) − b/2·(z2²−z1²)` then `y_application = yMoment/R_passive`. I independently re-derived the centroid: for σ(z)=a·z+b over [z1,z2], ∫z·σ dz = a/3(z2³−z1³) + b/2(z2²−z1²), and with y = terrainSurfaceY − z the first moment about y=0 is `terrainSurfaceY·force − ∫z·σ dz`, which matches the code exactly — the code is scientifically correct and an improvement over the doc. Only the `R_passive ≤ 0` fallback `axis.tip.y + (yIntersect − axis.tip.y)/3` (stage6-bishop.js:802) corresponds to the doc's 1/3 rule. Fix direction: update the doc to describe the multi-layer integration and exact centroid as the implemented method, keeping the 1/3 rule only as a documented fallback.
- **Recommendation:** Update doc §5.1/§5.4 to the multi-layer/exact-centroid method actually implemented; the code is correct and need not change.

### [WALLS-C-04] low · `passiveSide` direction-inference promised by the doc is not implemented (explicit only)
- **Location:** Doc §4.1 ("The solver can infer this from the slip direction, but explicit specification avoids ambiguity"). Code `src/lib/cpt-app/stage6-bishop.js:583-584` (`normalizePassiveSide` defaults to `'right'`), `:805,809` (uses stored `passiveSide` verbatim)
- **Category:** C — Doc vs code
- **Confidence:** confirmed
- **Analysis:** The doc says the passive side may be inferred from the slip direction. The code never infers it — `normalizePassiveSide(side)` simply returns `'left'` if explicitly `'left'`, otherwise `'right'` (defaulting to right). - **Recommendation:** Soften the doc or implement inference; align with the WALLS-A-02 sign fix.

### [WALLS-A-05] info · `circleWallSegmentIntersections` tangent threshold compares a squared discriminant against a linear epsilon
- **Location:** `src/lib/cpt-app/wall-geometry.js:131-133` (`disc = b*b − 4*c; if (disc < −eps) return []; const roots = disc <= eps ? [−b/2] : [...]`)
- **Category:** A — Implementation
- **Confidence:** confirmed (behaviour), low (impact)
- **Analysis:** `disc` has units of m² (it is `b²−4c` where b≈distance, c≈distance²), but the tangent test `disc <= eps` uses the default `eps = 1e-9`. So the single-root branch only fires for essentially exact tangency, and for a slightly grazing circle two near-identical roots are produced — handled by the dedup filter at line 136 (`Math.abs(other − s) <= eps`, also 1e-9, in metres). This is internally consistent and harmless for typical radii, but the mixed dimensionality means the "tangent" tolerance is not a true geometric tolerance (it does not scale with radius). The sibling implementation `activeCircleWallAxisIntersections` (stage6-bishop.js:686-718) uses the same pattern, so behaviour is at least consistent across the two copies. No correctness defect found; noted for rigor.
- **Recommendation:** None required; if hardened, scale the tangent/dedup tolerance by radius (e.g. `eps·R`).

## Notes / limitations of this audit pass
- I read `wall-geometry.js` in full and the wall-relevant sections of the large consumer files (stage6-bishop.js, mesh.js, solver.js, seepage/*). I did not exhaustively read all 18k lines of legacy-controller.js — only the wall-tagged references (grep-located) and the draw/passive-force sites. A wall input-validation or UI-side sign convention I did not see could change the severity of WALLS-A-02/A-03.
- WALLS-A-02 and WALLS-A-03 severity hinges on whether `passiveSide:'left'` and right→left slide directions are actually reachable from the shipping UI; I confirmed `passiveSide` is user-settable and that `moveSign` is not normalised, but did not trace every UI entry point. A second pass should construct a `passiveSide:'left'` test case and observe whether Spencer FS moves the correct direction.
- The beam-element math itself (consistent stiffness, B-matrix, the wall rotation DOF assembly into the global system) lives in `beam.hpp`/def-cpp-core and the WASM wire-format, which are outside this subsystem's named files; I verified only the JS-side geometry, DOF allocation (`wallRotationDofByNode`, `ndofTotal`), and activation gating in mesh.js. The numerical correctness of the beam stiffness coupling was not audited here.
- I did not run the code or the existing wall tests; all findings are from static reading. The centroid and circle/segment intersection math (WALLS-C-02, WALLS-A-05) were re-derived by hand and confirmed.
