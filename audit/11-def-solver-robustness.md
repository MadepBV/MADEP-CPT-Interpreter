## Overview
This subsystem is in good overall health. The strength-reduction primitive (`reduceMaterialStrengthForSafety`) matches the governing equations exactly (c/ΣMsf, tanφ/ΣMsf, tanψ/ΣMsf with ψ≤φ clamp, σt/ΣMsf with the c/tanφ cap), the bracketing search correctly reports the conservative lower-bound ΣMsf as FoS=SRF, and the production finalization classifier correctly separates physical mechanism from numerical non-convergence per the doc table. The most significant issue is a semantic mismatch between the safety-curve scalar fields the JS solver emits (`uMaxAbs`, `maxDeltaPlasticStrain` are **per-step increments relative to the previous accepted checkpoint**) and what the consuming plateau/mechanism-growth detectors and the documentation expect (**cumulative relative to the safety base**). This degrades plateau and mechanism-growth scoring and is a likely JS↔WASM parity divergence. A second cluster of low-severity issues are diagnostic-only inconsistencies between the 2D MC indicator in `post.js` and the canonical 3D indicator it claims to mirror. Arc-length is correctly absent from the executed JS path (the docs are explicitly forward-looking "design" specs), so no arc-length code-vs-doc defects exist yet.

## Findings

### [DEF-SOLVER-ROBUSTNESS-A-01] high · Safety-curve `uMaxAbs` / `maxDeltaPlasticStrain` are per-step increments, but plateau and mechanism-growth scoring treat them as cumulative-from-base
- **Location:** `src/lib/cpt-app/deformation/safety-finalization.js:80-93` (`plateauEvidence`), `src/lib/cpt-app/deformation/safety-mechanism.js:279-287` (`plasticGrowthOverWindow`), feeding from `src/lib/cpt-app/deformation/solver.js:5499-5523` (`extractIncrementalMechanismMetrics`) and `solver.js:7255,7262-7263` (curve build)
- **Category:** A — Implementation (with a C/doc dimension; see C-01)
- **Confidence:** confirmed (JS path)
- **Analysis:** In the JS solver the safety-search `stableCheckpoint` is advanced to the latest accepted state on every successful step (`solver.js:5759`), and each trial's metrics are computed as `extractIncrementalMechanismMetrics(stableCheckpoint, phase)` (`solver.js:5737`). Therefore `incrementalDisplacementMaxAbs` and `maxAccumulatedPlasticIncrement` are **per-step** increments relative to the immediately preceding accepted checkpoint, not cumulative from the safety base. These values are copied verbatim into the curve points: `uMaxAbs: trial.incrementalDisplacementMaxAbs` (`solver.js:7255`) and `maxDeltaPlasticStrain: trial.maxAccumulatedPlasticIncrement` (`solver.js:7262`).
  The consumers assume cumulative monotone series:
  - `plateauEvidence` (safety-finalization.js:80-83): `uGrowth = last.uMaxAbs - first.uMaxAbs`, `plasticGrowth = last.maxDeltaPlasticStrain - first.maxDeltaPlasticStrain`. Differencing two per-step increments is not "growth of displacement over the window."
  - `plasticGrowthOverWindow` (safety-mechanism.js:285-286): same `last - first` over `maxDeltaPlasticStrain`, then fed into `plasticGrowthScore` (safety-mechanism.js:397) which is 15% of the mechanism score.

  The doc is explicit that these must be cumulative: strength-reduction-msf-safety.md:297-299 ("max absolute nodal displacement increment **relative to safety base**"), and lines 358-367 define `maxSafetyPlastic_k` as cumulative from the safety-base checkpoint, with the note "This makes `maxSafetyPlastic_last - maxSafetyPlastic_first` the plastic growth over the plateau window, not a change in plastic strain rate." The code instead computes `last - first` over per-step increments, i.e. exactly the "change in plastic strain rate" the doc warns against. Result: plateau/mechanism-growth detection is keyed off increment-of-increments, which can both falsely trigger (per-step displacement naturally accelerates near failure, so `last-first>0`) and falsely fail to trigger (if the latest per-step increment dips). The impact is bounded because `plateau.detected` only changes the finalization status when `hasRejectedTrial` is false AND the mechanism is coherent (safety-finalization.js:148), and `plasticGrowthScore` is only 15% of the score — hence high, not critical.
- **Recommendation:** Make the safety-curve `uMaxAbs`/`maxDeltaPlasticStrain` cumulative from the safety base (compute `extractIncrementalMechanismMetrics(safetyBaseCheckpoint, phase)` for the curve-emitted values, keeping the per-step metrics only for the existing `safetyMechanismPlateauDetected` rate test that genuinely wants per-step deltas), or change the consumers to operate on per-step series. Either way, JS and WASM must agree (see C-01). Add a regression fixture asserting `uMaxAbs` is monotone non-decreasing across accepted curve points.

### [DEF-SOLVER-ROBUSTNESS-A-02] low · 2D `mohrCoulombIndicator` applies the tension cut-off unconditionally, ignoring `useTensionCutoff`
- **Location:** `src/lib/cpt-app/deformation/post.js:161-169` and `145-152`
- **Category:** A — Implementation (diagnostic path)
- **Confidence:** confirmed
- **Analysis:** The 2D indicator enters the tension-cutoff branch whenever `s3 < -sigmaTAllow - tensionTolerance`, with no `useTensionCutoff` gate. Its own comment (post.js:158-160) states it should match the three-regime split in `mohrCoulombIndicator3D`, but the canonical 3D version gates the cutoff: `if (useTensionCutoff && T3 > tensionTolerance)` (material-models.js:2504) and `onTensionBoundary = useTensionCutoff && T3 >= -tensionTolerance` (material-models.js:2525). For a material with `useTensionCutoff===false` but the default `sigmaTAllow===0`, any tensile minor principal stress (`s3<0`) makes the 2D indicator report `state:'tension-cutoff', F=∞, eta=∞`, whereas the 3D indicator would report a normal shear-MC state. This path is diagnostic-only: it is used at `solver.js:6082` and `6167` solely as a fallback when `response.update.diagnostics.mc` is absent, so it does not drive the return-mapping. Hence low.
- **Recommendation:** Pass and honor `useTensionCutoff` in the 2D indicator (or have it read `material.useTensionCutoff`) so its tension regime matches the 3D indicator it documents itself as mirroring; alternatively, delete the fallback and always use the diagnostics-supplied `mc`.

### [DEF-SOLVER-ROBUSTNESS-B-01] low · Depth-band `tauOverStrength` arrays accumulate every Gauss point then sort per band; `_tauValues` retained on working bands
- **Location:** `src/lib/cpt-app/deformation/diagnostics-depth-bands.js:200,116-137`
- **Category:** B — Performance/Memory
- **Confidence:** confirmed
- **Analysis:** `computeDepthBandReport` pushes one `tauRatio` per material point into `band._tauValues` (line 200) and later sorts each band's array (line 119) to compute p50/p95. This is O(n log n) over all integration points and allocates an array proportional to the integration-point count per report. It runs once per result build and once per depth-band history snapshot, so it is not a hot-loop leak, but for large meshes with frequent depth-band history (`initialPhase.depthBandHistory`) the repeated full sort and array retention is avoidable. `stripWorkingFields` (line 116) builds new objects without `_tauValues`, so the working copy is dropped — no persistent leak. Severity low.
- **Recommendation:** If depth-band history is captured per accepted step, consider streaming quantile estimation (e.g. P² algorithm or a fixed histogram over the known `[0, ~2]` clamp range) instead of storing+sorting all values per band per snapshot.

### [DEF-SOLVER-ROBUSTNESS-C-01] medium · Doc requires safety-base-relative monitor `u` and cumulative `maxSafetyPlastic`; JS code emits per-step increments (likely JS↔WASM divergence)
- **Location:** doc `docs/features/strength-reduction-msf-safety.md:297-299,347-367`; code `src/lib/cpt-app/deformation/solver.js:5737,5759,7255,7262-7263`; WASM decode `src/lib/cpt-app/deformation/wasm/wire-format.js:651-714`
- **Category:** C — Doc vs code
- **Confidence:** confirmed (JS side); likely (WASM divergence)
- **Analysis:**
  1. **Doc says:** `u_monitor = max absolute nodal displacement increment relative to safety base` (lines 297-299); `maxSafetyPlastic_k = max over Gauss points of accumulatedPlasticStrain_at_curve_point_k − accumulatedPlasticStrain_at_safety_base` — explicitly "cumulative from the safety-base checkpoint … not a per-step increment" (lines 358-367).
  2. **Code does:** The JS curve sets `uMaxAbs`/`maxDeltaPlasticStrain` from per-step `extractIncrementalMechanismMetrics(stableCheckpoint, phase)` where `stableCheckpoint` advances each accepted step — i.e. relative to the previous accepted state, not the base.
  3. **Which is correct:** The doc is scientifically correct. A monitored displacement curve `u` vs `ΣMsf` must be monotone-in-history to visualize the plateau (strength-reduction-msf-safety.md:264-272, "displacement grows strongly while ΣMsf stops increasing"); per-step increments do not give a stabilization curve. The WASM v7 wire contract also documents these as base-relative; if the C++ encoder produces cumulative values while JS produces per-step values, the same `plateauEvidence`/`plasticGrowthOverWindow` helpers behave differently on the two backends — a parity defect the doc's acceptance criteria forbid (strength-reduction-msf-safety.md:1078, "`relativeResidual` uses the same per-step initial residual definition in WASM and JS consumers" — analogous parity intent).
  4. **Fix direction:** Fix the JS code (compute base-relative cumulative values for emitted curve fields) and add a JS↔WASM parity fixture on `uMaxAbs`/`maxDeltaPlasticStrain`. See A-01.

### [DEF-SOLVER-ROBUSTNESS-C-02] medium · WASM finalization-mode default diverges from JS solver default when the option is absent
- **Location:** code `src/lib/cpt-app/deformation/solver.js:6504` vs `src/lib/cpt-app/deformation/wasm/build-result.js:584` and `src/lib/cpt-app/deformation/safety-finalization.js:12-19,114`
- **Category:** C — Doc vs code (and JS↔WASM consistency)
- **Confidence:** confirmed
- **Analysis:** The JS solver coerces a missing `safetyFinalizationMode` to `'production-msf'` (`normalizeSafetyFinalizationMode(input?.options?.safetyFinalizationMode, 'production-msf')`, solver.js:6504). The WASM build-result passes `mode: options.safetyFinalizationMode` straight into `buildSafetyFinalization` (build-result.js:584) without normalization. Inside `buildSafetyFinalization`, `normalizeSafetyFinalizationMode(mode)` is called **without** the production fallback (safety-finalization.js:114), so a `null`/`undefined` mode resolves to `'legacy-bracket'` (the function's hard default at line 13). Net effect: if `options.safetyFinalizationMode` ever reaches the WASM result builder undefined, the WASM backend silently classifies in `legacy-bracket` while the JS backend would use `production-msf` for the identical input — different reported `finalization.status`. The doc (strength-reduction-msf-safety.md:206-214) intends the default to be a single explicit migration decision, not a backend-dependent accident. In current practice the controller sets the option explicitly (`legacy-controller.js:4406,8386`), so this is latent, hence medium not high.
- **Fix direction:** Fix code — normalize `safetyFinalizationMode` once in the WASM options pipeline (mirroring solver.js:6504), or make `buildSafetyFinalization`'s internal `normalizeSafetyFinalizationMode(mode)` call share the same default policy across both call sites.

### [DEF-SOLVER-ROBUSTNESS-C-03] medium · `plateauWindowStart`/`plateauWindowEnd` can be non-null while `plateauDetected` is false
- **Location:** `src/lib/cpt-app/deformation/safety-finalization.js:168-170`
- **Category:** C — Doc vs code (internal contract)
- **Confidence:** confirmed
- **Analysis:** The returned object sets `plateauDetected: status === 'mechanism-developed' && (plateau.detected || rawFinalStatus === 'mechanism-developed')` (line 168), but `plateauWindowStart`/`End` are gated only on `plateau.detected` (lines 169-170), independent of `status`. So a result with `status:'bracketed-failure'` but `plateau.detected===true` reports `plateauDetected:false` yet `plateauWindowStart`/`End` non-null. The `SafetyFinalization` contract (strength-reduction-msf-safety.md:687-706) and UI requirement (lines 901-905, "Mark the plateau window") imply the window markers should describe the plateau the finalizer actually acted on. A consumer marking the plateau window on the curve would draw a window for a non-plateau result.
- **Fix direction:** Fix code — gate `plateauWindowStart`/`End` on the same condition as `plateauDetected` (return `null` when `plateauDetected` is false), or define and document them as raw evidence independent of the final status. Prefer aligning with `plateauDetected`.

### [DEF-SOLVER-ROBUSTNESS-C-04] low · 2D vs 3D MC indicator disagree on the F=0 / eta=1 boundary classification
- **Location:** `src/lib/cpt-app/deformation/post.js:180-182` vs `src/lib/cpt-app/deformation/material-models.js:2526-2528`
- **Category:** C — Doc vs code (cross-module consistency)
- **Confidence:** confirmed
- **Analysis:** The 2D indicator labels `'mc-yield'` when `eta >= 1` (post.js:180), i.e. boundary-inclusive. The 3D indicator labels `'mc-yield'` when `F > 0` (material-models.js:2526), i.e. boundary-exclusive (`F===0` → elastic/tension-boundary). Since `eta>=1 ⟺ F>=0` for `denom>0`, the two differ exactly at the yield boundary `F=0`. post.js:158-160 claims the indicators match. The discrepancy is at a measure-zero boundary and the 2D path is diagnostic-fallback only, so the practical impact is negligible — but it is a stated-equivalence that does not hold.
- **Fix direction:** Fix code (use a consistent boundary convention, preferably `F > 0` to match the 3D canonical), or relax the comment claiming exact equivalence.

### [DEF-SOLVER-ROBUSTNESS-C-05] low · `safetyMechanismPlateauWindow` default differs between solver (3) and finalization/mechanism helpers (4)
- **Location:** `src/lib/cpt-app/deformation/solver.js:5526` (default 3) vs `src/lib/cpt-app/deformation/safety-finalization.js:6,62` (default 4) and `src/lib/cpt-app/deformation/safety-mechanism.js:282` (default 4)
- **Category:** C — Doc vs code (internal default consistency)
- **Confidence:** confirmed
- **Analysis:** `safetyMechanismPlateauDetected` in the solver uses `Math.round(options.safetyMechanismPlateauWindow) || 3` (solver.js:5526), while `plateauEvidence` (safety-finalization.js:62) and `plasticGrowthOverWindow` (safety-mechanism.js:282) default the same option to 4. The doc recommends `plateauWindow = 4 accepted points` (strength-reduction-msf-safety.md:381). When the option is unset, the solver-side early "mechanism-developed" trigger uses a 3-point window while the finalization/scoring layer uses a 4-point window, so the two plateau decisions are evaluated over inconsistent windows. Low because the option is usually supplied and the difference is one point.
- **Fix direction:** Fix code — unify the default to 4 (the doc value) across all three sites, or thread one shared constant.

### [DEF-SOLVER-ROBUSTNESS-C-06] low · Depth-band `eta`/`etaMax` become `+Infinity` on tension-cutoff points
- **Location:** `src/lib/cpt-app/deformation/diagnostics-depth-bands.js:180,197,199` consuming `material-models.js:2507` (`eta: +Infinity`)
- **Category:** C — Doc vs code (reporting robustness)
- **Confidence:** confirmed
- **Analysis:** On a tension-cutoff Gauss point `mohrCoulombIndicator3D` returns `eta: +Infinity` (material-models.js:2507). In the depth-band report, `eta = Number.isFinite(mc.eta) ? max(mc.eta,0) : +Infinity` (line 180), then `maxEta`/`band.etaMax` take `Math.max(..., Infinity)` → `+Infinity` (lines 197,199). The depth-band report's `maxEta`/`etaMax` thus serialize as `Infinity`. The path-following doc (solver_robustness_path_following.md §4 and §7.4) intends depth-band diagnostics to be interpretable engineering numbers and explicitly warns against conflating local `eta_MC` saturation with global failure (line 546). `Infinity` in a numeric report field is fragile for JSON/serialization/UI. `chooseDominantBand` does not use `etaMax`, so scoring is unaffected. Low.
- **Fix direction:** Fix code — cap or sentinel the reported eta (e.g. clamp to a large finite value or report a separate `tensionCutoffCount`) rather than propagating `Infinity` into `maxEta`/`etaMax`.

### [DEF-SOLVER-ROBUSTNESS-C-07] low · `tauOverStrength` uses |τxy| and mean stress, not max shear and the actual failure-plane normal stress
- **Location:** `src/lib/cpt-app/deformation/diagnostics-depth-bands.js:86-95`
- **Category:** C — Doc vs code (diagnostic fidelity)
- **Confidence:** confirmed
- **Analysis:** `tauOverStrength` computes `tau = |txy|` (the Cartesian shear component) and `sigmaN = max(0, 0.5*(sxx+syy))` (the in-plane mean stress p), then `strength = c + sigmaN*tanφ`. The Mohr-Coulomb mobilized-strength ratio should compare the maximum shear stress (`τ_max = r = hypot(0.5*(sxx−syy), txy)`, already computed as `radius` in `principalStress2DCompressionPositive`, post.js:131-143) against `c + σn·tanφ` on the critical plane, not `|τxy|` against `c + p·tanφ`. As written, a state with large `σxx−σyy` but small `τxy` reads as low `tauOverStrength` despite being near MC failure. The docs do not define this exact ratio, so this is a fidelity concern in a named field ("tauOverStrength"), not a standards violation; the band also reports the proper `etaMax` (which is the true MC mobilization). Low.
- **Fix direction:** Fix code — use the maximum shear stress (deviatoric radius) and a defensible normal stress, or rename the field to make the |τxy|/mean-stress heuristic explicit. Given `eta` already encodes true MC mobilization, consider deriving the ratio from `eta`.

### [DEF-SOLVER-ROBUSTNESS-C-08] info · Reported safety FoS is clamped to ≥ 1; a failed first probe and a true FoS≈1 are indistinguishable
- **Location:** `src/lib/cpt-app/deformation/safety-finalization.js:116` (`Math.max(..., 1)`); `src/lib/cpt-app/deformation/solver.js:5643,5808-5811,5836-5839`
- **Category:** C — Doc vs code (interpretation)
- **Confidence:** confirmed
- **Analysis:** `factorOfSafetyLower` is forced to `≥1` (safety-finalization.js:116), consistent with the ΣMsf≥1 domain (strength-reduction-msf-safety.md:85, arc-length doc:134-141). The search starts at `lowerSigmaMsf = 1` (solver.js:5643) from a converged self-weight/service base (enforced at solver.js:6993-7034). If the very first reduced-strength trial (ΣMsf slightly >1) fails, the reported FoS is exactly `1.0` with an upper bracket just above it — which is the correct conservative statement but is numerically indistinguishable from a structure whose true FoS is, e.g., 1.0001, and cannot express FoS<1 (a structure already failing under service load is gated out earlier, so this is by design). This is an inherent c-φ-reduction limitation, documented implicitly; noting for engineering interpretation, not a bug.
- **Fix direction:** Doc/UI — when `factorOfSafetyLower === 1` and an upper bound exists, surface explicit "FoS ≈ 1 (at or below the smallest tested reduction)" wording so users do not read it as a comfortable margin.

### [DEF-SOLVER-ROBUSTNESS-C-09] info · `buildSafetyFinalization` is called without `curve` per-point `index` guarantees; plateau window indices fall back to positional values
- **Location:** `src/lib/cpt-app/deformation/safety-finalization.js:96-98`; JS curve `src/lib/cpt-app/deformation/solver.js:7238-7240`
- **Category:** C — Doc vs code (contract robustness)
- **Confidence:** confirmed
- **Analysis:** `plateauEvidence` sets `start`/`end` from `Number(first.index)`/`Number(last.index)` falling back to positional `points.length - window.length` / `points.length - 1` (safety-finalization.js:96-98). The JS curve assigns `index` as the **sequential index over converged points** (solver.js:7238 `index`) and a separate `trialIndex` for the trial number (solver.js:7239). The wire/doc contract (strength-reduction-msf-safety.md:624-653) treats `SafetyCurvePoint.index` as the canonical accepted-equilibrium step index and `trialIndex` as the trial. The JS assignment is self-consistent (index = position in the converged-curve array), so `plateauWindowStart/End` are valid array positions — but a consumer interpreting `plateauWindowStart` as a `trialIndex` would mis-map. No defect today; noting because the dual index/trialIndex semantics are easy to confuse across the JS and WASM emitters.
- **Fix direction:** Doc — clarify which index space `plateauWindowStart/End` live in; ensure WASM emits `index` in the same accepted-curve-position space as JS.

I did not attempt to verify the C++ Phase-5/6/7 arc-length status.
- I verified `reduceMaterialStrengthForSafety` (material.js:163-196) against the governing equations and the strength-reduction doc (§3.2 of solver_robustness_path_following.md, and strength-reduction-msf-safety.md:75-81): c/Σ, tanφ/Σ→arctan, tanψ/Σ→arctan with ψ≤φ clamp, σt cap c/tanφ then /Σ, ΣMsf≥1 clamp — all correct. - The mechanism scoring weights (safety-mechanism.js:399-404) match the doc's convex combination (0.35/0.20/0.15/0.15/0.15, sum 1.0) and thresholds (0.65/0.40) exactly; `buildSafetyMechanismElementNeighbors` correctly caches on the mesh and uses corner-node shared-edge adjacency per the doc. No defects found there beyond the per-step-vs-cumulative input issue (A-01/C-01).
- A focused second pass on JS↔WASM safety-curve numeric parity (a fixture comparing `uMaxAbs`, `maxDeltaPlasticStrain`, `mechanism.score`, and `finalization.status` between backends on an identical converging safety case) would be the highest-value follow-up.
