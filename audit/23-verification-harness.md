## Overview
The harness is a mixed bag of genuinely excellent independent oracles and several mislabeled "verification"/"parity" scripts that cannot actually fail. The best work is real: `verify_seepage_phase_2.mjs` checks against the closed-form Dupuit free-surface parabola; `verify_wall_beam_analytical.mjs` checks cantilever tip deflection/rotation against `F·L/EA`, `M·L/EI` at 1e-9 and a Rankine `M∝s³` field; `verify_deformation_phase_1.mjs` rebuilds elastic matrices and return-mapping oracles independently; `verify_hs_tangent_oracle.mjs` and the Simo-Hughes/arc-length C++ harnesses do central-difference tangent parity against the shipped algorithm. The serious weaknesses are: (1) two scripts that compute discrepancy metrics but never assert and never set a non-zero exit code (`verify_wasm_cpu_parity.mjs`, `validate-pile.js`) — they look like gates but always "pass"; (2) the only slope-stability test (`verify_bishop_phase_a_parity.mjs`) is a refactoring-equivalence check between two soil-sampling paths of the *same* Bishop/Spencer solver, so the FS formula has no independent oracle anywhere; (3) `verify_integrated_plan.mjs` is largely source-text regex grepping of `solver.js`, which guards token presence, not behavior; (4) the default-CI HS tangent oracle accepts 35% relative tangent error on the production continuum path. There is no CI workflow at all, and ~21 verify scripts are orphaned from any `package.json` target, so the entire suite is opt-in manual invocation.

## Findings

### [VERIFICATION-HARNESS-A-01] high · `verify_wasm_cpu_parity.mjs` computes parity metrics but never asserts and always exits 0
- **Location:** `scripts/verify_wasm_cpu_parity.mjs:198-232` (diff loop), `:199-201` (`FAIL:` only logs + `continue`), `:234-240` (only exit(1) is in the top-level `catch`)
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** The script header calls itself "End-to-end parity verification". It runs the CPU JS path and the WASM CPU path on the same model, computes `diff.maxDelta`, `diff.rmsDelta`, `rel`, settlement deltas, and plastic-element counts, and `console.log`s all of them — but there is no tolerance, no threshold, and no assertion anywhere. The only failure branch (`if (!diff.ok) { console.error('FAIL:', diff.reason); continue; }`) just logs a mesh-size mismatch and continues to the next case. `grep -nE "process.exit|throw|assert"` over the file returns exactly two hits: line 200 (`console.error('FAIL:', ...)` — no exit) and line 239 (`process.exit(1)` inside `main().catch(...)`, only reached if the WASM module fails to load or an exception is thrown). Consequently CPU and WASM can disagree by any amount — even diverge completely — and the script exits 0. It is purely diagnostic but is presented (shebang, name, header) as a runnable regression gate. Mitigating: it is not wired into any `package.json` target, so it is not silently passing an automated CI (there is no CI).
- **Recommendation:** Add a relative-difference threshold (e.g. `rel <= 1e-3` for elastic, a documented looser bound for plastic) and set `process.exitCode = 1` on breach and on the mesh-size-mismatch `FAIL` branch; or rename/relabel the file explicitly as a diagnostic so it is not mistaken for a gate.

### [VERIFICATION-HARNESS-A-02] high · `validate-pile.js` discards every `check()` result and always exits 0
- **Location:** `scripts/validate-pile.js:18-25` (`check` returns `ok` but callers ignore it), `:112-323` (all `check(...)` call sites), no `process.exit`/aggregation anywhere
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `check(label, actual, expected, tolPct)` prints a ✓/✗ glyph and `return ok`, but no call site stores or aggregates the return value (the only use of the boolean is line 321, `if (!(ok1 && ok2)) console.log(...)`, which only prints extra diagnostics). There is no `let failures`, no `process.exit(1)`, and no non-zero exit on any failed check. `grep -nE "process.exit|exitCode"` over the file returns nothing. Therefore if the pile module produced wrong `R_b`, `R_s`, `R_c_d`, ξ values, etc., every check would print ✗ and the script would still exit 0. The pile factor expectations in the file do match the source tables I cross-checked (`stage6-pile.js`: sand `q_s = 110 + 4·(qc-10)` at line 200; ξ for `'1-3'/'1/100m2'` → 1.32/1.23; cfa sand `α_b=0.60`; cfa-none `γ_Rd=1.35`), so the assertions are correct in content — but the harness cannot enforce them. Combined with the file not being referenced in `package.json`, the only failure signal is a human reading console glyphs.
- **Recommendation:** Accumulate `ok` results (e.g. `allOk &&= check(...)`) and `process.exit(allOk ? 0 : 1)` at the end. Wire it into a `verify:pile` npm target.

### [VERIFICATION-HARNESS-A-03] high · Default-CI HS tangent oracle accepts 35% relative tangent error on the production continuum path
- **Location:** `scripts/verify_hs_tangent_oracle.mjs:58` (`USE_SIMO_HUGHES = process.env.MADEP_HS_USE_SIMO_HUGHES === '1'` → false by default), `:767-769` (cone `relErr < 0.35`), `:821-824` (corner `relErr < 0.35`)
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** This script is verifier #10 in the production-acceptance gate (`verify_hs_acceptance.mjs:44`) and is the harness's primary algorithmic-tangent check (analytic tangent vs central-difference FD oracle, a genuinely independent oracle built from the real stress-update calls). However, the acceptance tolerance for the cone and corner cases is branch-dependent: when `USE_SIMO_HUGHES` is false (the **default**, because the env var is unset in a plain `node`/`npm run` invocation), the cone tolerance is `relErr < 0.35` and the corner tolerance is `relErr < 0.35` — i.e. a 35% relative Frobenius deviation between the *production* analytic continuum tangent and the FD oracle is accepted. This is by design (the comment at lines 28-39 documents that the continuum tangent is not the consistent/algorithmic tangent for non-associated plasticity, so a large FD gap is expected), and the production solver does dispatch to `HsTangentMode.Analytic` by default (confirmed in `src/.../deformation/solver.js` and `gpu/v2`). The consequence is real: for the default production path, this oracle only catches gross tangent errors (>35%); a meaningfully wrong analytic tangent (e.g. a sign error in one block, or a 20% miscalibration that still degrades Newton convergence) passes. The tight 1e-4 gate only applies when `MADEP_HS_USE_SIMO_HUGHES=1`, which is not the default. The elastic (1e-6) and cap-only (1e-6) cases remain tight.
- **Recommendation:** Either make `MADEP_HS_USE_SIMO_HUGHES=1` the default for the acceptance run (so the tight 1e-4 tangent parity is the gate that ships), or add an independent quadratic-convergence-rate assertion for the continuum path (Newton residual contraction ratio) so tangent quality is bounded by a meaningful proxy rather than a 35% Frobenius band.

### [VERIFICATION-HARNESS-A-04] low · `verify_deformation_phase_1.mjs` prints "passed" even when `CASE_FILTER` skips all cases
- **Location:** `scripts/verify_deformation_phase_1.mjs:268` (`CASE_FILTER`), `:270-274` (`runCase` returns early on non-match), `:2321` (`console.log('... verification passed.')`)
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `runCase` skips (`return`) any case whose name does not include the `CASE_FILTER` env string. If `CASE_FILTER` is set to a value matching no case (typo, stale filter), every case is skipped, no assertion runs, and the script reaches `console.log('Deformation Phase 1 verification passed.')` and exits 0. This is a dev affordance (the same pattern is harmless when used correctly), but it means a green exit does not guarantee any assertion executed. Failures of executed cases do gate correctly (top-level `await` + throwing `assert` → unhandled rejection → non-zero exit), so this is low severity.
- **Recommendation:** Track the number of cases actually run and exit non-zero (or warn loudly) if zero ran while `CASE_FILTER` was set.

### [VERIFICATION-HARNESS-C-01] high · `verify_bishop_phase_a_parity.mjs` is a refactor-equivalence test, not a correctness oracle — the Bishop/Spencer FS formula has no independent check anywhere
- **Location:** `scripts/verify_bishop_phase_a_parity.mjs:248-269` (both runs are `analyzeBishopSearch` differing only by `soilSource: 'legacy-bands'` vs `'regions'`); cross-ref `src/lib/cpt-app/stage6-bishop.js:283-290, 371, 2516, 2563` (the `soilSource` branch only selects how soil/weights are sampled; the FS solver, `M_alpha`, `ΣW·sinα`, Spencer-λ iteration are shared)
- **Category:** C — Doc vs code consistency (claim vs behavior)
- **Confidence:** confirmed
- **Analysis:** The script name and pass message ("Phase A parity verification passed") read as a verification of the slope-stability result. In reality it compares two soil-sampling implementations (the legacy banded sampler vs the polygon-region sampler) within the identical `analyzeBishopSearch` pipeline, then asserts the resulting `FS`, `F_bishop`, `F_m`, `F_f`, `lambda`, slice weights/areas match to 1e-6 relative. Because both paths feed the *same* Bishop-Simplified / Spencer numerics, any error in the FS formula itself (e.g. wrong `m_α = cosα(1 + tanα·tanφ/F)`, a sign in the `ΣW·sinα` driving moment, a Spencer interslice-force convention error) is present in BOTH sides and the parity test passes. I grepped the whole `scripts/` tree: no script anywhere asserts a Bishop or Spencer FS against an independent analytical/textbook value (e.g. a known homogeneous-slope FS, an infinite-slope `c'+γz cos²β tanφ' / γz sinβ cosβ`, or a published benchmark). The doc-vs-code mismatch: the harness presents itself as covering Bishop/Spencer correctness, but it only covers the soil-sampling refactor equivalence. The refactoring equivalence it does test is correct and useful; the gap is the absence of an absolute oracle. Scientifically, slope stability is exactly the kind of result where a plausible-but-wrong FS is dangerous, so this coverage gap matters.
- **Recommendation:** Keep the parity test (it is valid for the refactor), but add at least one absolute-FS regression: a homogeneous cohesive slope with a known limit-equilibrium FS, or an infinite-slope closed form, asserted to a tight tolerance.

### [VERIFICATION-HARNESS-C-02] medium · `verify_integrated_plan.mjs` is largely source-text regex grepping of `solver.js`, advertised as a "Regression suite" exercising "invariants"
- **Location:** `scripts/verify_integrated_plan.mjs:1-5` (header: "Regression suite … Each block exercises a specific invariant"), `:60-185` (Phases 1, 3, 4, 5, 6 are `RegExp.test(solverSource)` checks)
- **Category:** C — Doc vs code consistency (claim vs behavior)
- **Confidence:** confirmed
- **Analysis:** Of the file's `check(...)` calls, ~26 are `<regex>.test(solverSource)` / file-existence checks against the literal text of `src/lib/cpt-app/deformation/solver.js` (e.g. line 65 `/initialPhase\.canStartSafety\s*!==\s*true/`, line 113 a regex on the function signature, line 148 a regex on a ternary). These pass as long as the matched substring exists somewhere in the source; they do not execute the gate logic, so they cannot detect a behavioral regression — only the verbatim deletion/rename of a token. The header overstates this as exercising "invariants the integrated plan introduced or restored." The later blocks (Phase 2 tolerance helpers, the near-surface confining-stress floor, `initialEffectiveStress6AtPoint`, MC admissibility of the opt-in seed at lines 86-257) ARE genuine behavioral checks with real numerics, so the file is not worthless — but roughly half of it is structural string-matching presented as regression coverage. A source-grep check is also brittle: a refactor that splits a condition across lines or renames a local breaks the regex without any behavior change.
- **Recommendation:** Reframe the source-regex blocks in comments/output as "presence guards" distinct from behavioral assertions; where feasible, replace them with calls that actually exercise the gate (e.g. invoke the solver with a stress-only reference and assert it refuses to start safety) rather than asserting the rejection string exists.

### [VERIFICATION-HARNESS-C-04] low · `verify_safety_mechanism_summary.mjs` only checks the score *ordinally*, so a wrong score scale/formula is not caught
- **Location:** `scripts/verify_safety_mechanism_summary.mjs:99-100` (`localized.score > scattered.score`), `:97-98` (`connectedComponentCount` exact — good), `:110, 133` (`status === 'none'` — good)

### [VERIFICATION-HARNESS-C-05] low · NEN6740 round-trip cannot detect a wrong stress exponent (forward+inverse use the same constant)
- **Location:** `scripts/verify_nen6740.mjs:35-37` (`measuredQcForCentre` inverts using `NEN6740_STRESS_EXPONENT`), `:43-55` (round-trip), cross-ref `src/lib/cpt-app/nen6740.js:13` (`NEN6740_STRESS_EXPONENT = 0.67`, comment cites Deltares D-SHEET)
- **Category:** C — Doc vs code consistency
- **Confidence:** confirmed
- **Analysis:** The regression-slope check (lines 66-71) is actually meaningful — it confirms the hardcoded `NEN6740_RF_SLOPE = 0.34` agrees within 0.02 of the least-squares slope of `log10(qcNen)` vs `rf` over the 14 digitized centres, so it would catch a desynchronized coefficient. The round-trip check, however, builds `qc` from `qcNen` by inverting `computeNen6740Qc` with the *same* `NEN6740_STRESS_EXPONENT`, then reclassifies. If the exponent (0.67) were wrong, both the forward stress correction and the test's inverse would be wrong consistently, and the round-trip would still recover the same material order. So the exponent constant — the one with a real standards basis (the source comment notes 0.34 is *not* a published NEN coefficient) — is not independently validated by this script. Low severity because the exponent is a documented, stable constant.
- **Recommendation:** Add a fixed-input check: a known `(qc, σ'v)` pair with an independently computed `qcNen` (hand-calc or D-SHEET reference), so the exponent itself is pinned, not just the slope coefficient.

### [VERIFICATION-HARNESS-A-05] info · Bishop parity `approxEqual` falls back to `===` on non-finite values, which can mask NaN drift
- **Location:** `scripts/verify_bishop_phase_a_parity.mjs:11-16`
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `approxEqual` returns `a === b` when either value is non-finite. If both legacy and region paths produce `NaN` for the same field, `NaN === NaN` is `false`, which would (correctly) fail — but if one path yields `Infinity` and the other a finite number near the cap, the `===` short-circuit gives a hard mismatch rather than a tolerance-based one (acceptable). The subtler issue: `null`/`null` returns true (line 12), so two paths that both silently drop a field to `null` (e.g. both fail to compute `wallForceTotal`) compare "equal" and pass, hiding a shared regression. This is a minor robustness note on the comparator, not a confirmed bug.
- **Recommendation:** Consider failing (or warning) when a compared field is `null`/`undefined` on both sides for fields that are expected to be populated, so silent shared dropouts are visible.

## Notes / limitations of this audit pass
- I read the priority files in full and mapped the two largest (`verify_deformation_phase_1.mjs` 2321 lines, `verify_seepage_phase_2.mjs` 1040 lines) via grep plus targeted reads of their oracle/exit logic and representative cases; I did not read every one of their ~50 cases line-by-line, so a buried loose tolerance inside an individual deformation case could exist beyond what I sampled (the helper infrastructure and the cases I read were sound, with tight 1e-8/1e-9 tolerances and independent return-mapping oracles).
- I verified exit-code behavior for the flagged scripts directly (grep for `process.exit`, plus confirming top-level-await + throwing `assert` propagates to a non-zero exit under `"type":"module"`). The two "always exits 0" findings (A-01, A-02) are confirmed by absence of any aggregation/exit path.
- I confirmed the Bishop parity circularity by reading the `soilSource` branches in `stage6-bishop.js`; I did not exhaustively prove that *no* code path differs between `legacy-bands` and `regions` beyond soil sampling, but the FS solver and Spencer iteration are clearly shared, which is sufficient to establish the coverage gap.
- I did not benchmark runtime/memory of the harness scripts; no category-B (performance/leak) findings are reported because the scripts are short-lived CLI processes where leaks are immaterial, and I saw no pathological hot loops. Absence of B findings reflects scope, not a guarantee.
- The 35% tangent tolerance (A-03) is correct as read, but whether it is a *practical* risk depends on how far the production continuum tangent actually sits from FD in real solves; I confirmed the default branch and the tolerance, not the empirical margin, so the severity reflects "the gate is loose," not "the tangent is wrong."
