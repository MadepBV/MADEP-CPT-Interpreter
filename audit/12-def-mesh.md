## Overview
The deformation meshing subsystem is in good health and notably careful. The hardest correctness traps for a T6/LST upgrade — native Triangle `o2` midpoint ordering, the orientation-flip that must reorder midpoints together with corners, shared-edge midnode dedup, and full-edge-node constraints (so pinned corners don't leave a free mid-node) — are all handled correctly and are defended by a geometric `validateT6Element` assertion at build time and by a robust coordinate-keyed fallback for boundary midnode recovery. The element math (shape functions, B-matrix, Gauss weights) is internally consistent and consistent with the *newer* `T6_mesh.md` spec. The main issues are documentation: the older `T6_mesh_v1.md` describes a fundamentally different (superseded) implementation strategy whose node ordering and shape functions are incompatible with the shipped code, which is a real hazard for any future maintainer who reads v1. There are also several performance items (O(n²)/O(n³)-shaped PSLG dedup loops, repeated `cleanPolygon` calls) and minor metadata/dead-code observations. No correctness-critical defect was confirmed.

## Findings

### [DEF-MESH-A-01] medium · `cornerNodes` mesh-stat overcounts orphan mid-edge nodes for T6
- **Location:** `src/lib/cpt-app/mesh/section-mesh.js:409` (and `meshStats` at 407–424); `addMeshSanityWarnings` consumer `src/lib/cpt-app/deformation/mesh.js:610-614`
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `cornerNodes: resolvedElementType === 't6' ? nodes.length - midEdgeNodes.size : nodes.length`. `nodes` is built from the *full* Triangle `pointlist` (section-mesh.js:278-285), i.e. it includes every node Triangle emitted, including mid-edge nodes whose two adjacent triangles were both dropped (sliver-area filter at line 330, or centroid-outside-polygon filter at line 332). `midEdgeNodeIds` (line 366-374) only collects element[3..5] of *kept* elements. Therefore `nodes.length - midEdgeNodes.size` counts every dropped mid-edge node and every orphaned node as a "corner". The reported `cornerNodes` and `midEdgeNodes` then do not sum to a clean corner/midside partition, and `midEdgeNodes` undercounts. The downstream `nodesPerTriangle` sanity heuristic (mesh.js:610) and any UI display of node composition inherit this. This is a reporting/diagnostic inaccuracy, not a solver-correctness bug (the solver indexes nodes by element connectivity, never by these counts). The companion `t6RecoveredMidNodes` field documents that dropped-element cases are real and occur.
- **Recommendation:** Compute `cornerNodes` from the union of element[0..2] across kept elements (a `Set`), and derive `midEdgeNodes` from element[3..5] as today; orphan nodes then belong to neither bucket and can be reported separately. Alternatively subtract orphan count explicitly. Fix code (the doc-stated intent in `T6_mesh_v1.md` §2.7 is `nodes.length - originalCornerNodeCount`, which is also imperfect for orphans).

### [DEF-MESH-A-02] low · Free-DOF sanity guard ignores wall-rotation DOFs (under-reports for walled T6 meshes)
- **Location:** `src/lib/cpt-app/deformation/mesh.js:623` (`const approxFreeDofs = 2 * nodes;`)
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `attachMeshSanityWarnings` estimates T6 DOF load as `2 * nodes`. But `attachMechanicalWallsToMesh` (mesh.js:495) sets `mesh.ndofTotal = 2 * mesh.nodes.length + wallRotationDofByNode.size`, adding one rotational DOF per recovered wall node. The warning runs after `attachMechanicalWallsToMesh` (it is the last call in `buildDeformationMesh`, line 583), so `mesh.ndofTotal` is available but unused here. The guard therefore slightly under-reports the true free-DOF count for walled sections. The comment itself even calls `2 * nodes` an "upper bound; constrained DOFs subtract a small fraction" — which is the opposite sign of the wall-DOF effect (walls *add* DOFs). Cosmetic/threshold-only impact (50,000 DOF warning gate).
- **Recommendation:** Use `mesh.ndofTotal` (already computed) instead of `2 * nodes` for the guard. Fix code.

### [DEF-MESH-A-03] low · Secondary collinear-merge marker tie-break is effectively inert
- **Location:** `src/lib/cpt-app/mesh/section-pslg.js:334-340`
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** In the collinear-overlap merge, `winnerMarker = (a.markerId||0) <= (b.markerId||0) ? a : b` is computed (line 335) but the `survivor` (line 336-340) is built from `mergeRefinement(winnerPriority, winnerMarker === winnerPriority ? a : b)`. `mergeRefinement` only merges `segmentTargetLength`; it spreads `...winnerPriority` for all other fields including `markerId`. So the survivor always inherits `winnerPriority`'s marker, never `winnerMarker`'s. The intended "lowest markerId wins on a priority tie" rule (which the *primary* dedup at line 278 does honor) is not applied in the secondary merge. Effect is benign in practice: when priorities differ, the higher-priority segment is the desired marker carrier anyway; only on an exact priority tie between two collinear-overlapping segments with different markers does the chosen marker become order-dependent. Since markerIds map back to boundary/region metadata used for support/traction tagging, an order-dependent pick is a latent (currently low-impact) inconsistency.
- **Recommendation:** If a deterministic marker is desired on priority ties, base the survivor's `markerId` on `winnerMarker.markerId` explicitly, or drop the dead `winnerMarker` computation if the priority-only rule is intended. Fix code (or remove dead variable — see DEF-MESH-D-02).

### [DEF-MESH-B-01] medium · `splitConstraintSegments` is O(n²) over all PSLG segments with per-pair full intersection work
- **Location:** `src/lib/cpt-app/mesh/section-pslg.js:177-215`
- **Category:** B — Performance
- **Confidence:** confirmed
- **Analysis:** The split pass double-loops every constraint-segment pair (`for i; for j=i+1`). It has a bbox-overlap early-out (lines 190-191), so it is not pathological in the typical case where segments are spatially separated, but the input is the *post-densify-precursor* segment set built from outer boundary pieces + region polygon edges + wall stations + (importantly) load-refinement-driven terrain splits. For a wide section with several surface loads the terrain edge is split into many pieces (`buildLoadRefinementMeta`/`splitTerrainEdgeAtXs`) and region polygons can be detailed, so n can grow into the hundreds-to-thousands and the worst case (many overlapping/collinear terrain+region segments sharing a y-band) defeats the bbox filter. Each surviving pair runs `segmentIntersection` plus up to four `pointOnSegment` calls. This runs once per meshing *attempt* (up to 4 attempts), inside `buildMechanicalPslg` which is itself re-invoked per attempt. It executes on the worker thread, so it does not block the UI, but it is the most likely hot spot in mesh prep on large sections.
- **Recommendation:** Spatially index segments (uniform grid / sweep line on x) before the pairwise test, or bucket by the shared y-band for terrain/region collinear cases. Confidence on the *existence* of the O(n²) loop is confirmed; the severity depends on real section sizes, hence medium.

### [DEF-MESH-B-02] medium · `dedupeSegmentsByPriority` collinear-merge is O(n³)-shaped (`while(changed)` over an O(n²) pairwise scan that restarts on every merge)
- **Location:** `src/lib/cpt-app/mesh/section-pslg.js:294-353`
- **Category:** B — Performance
- **Confidence:** confirmed
- **Analysis:** After the primary hash dedup, the secondary collinear merge runs `while (changed) { ... outer: for i { for j>i { if mergeable { merge; break outer } } } }`. Each successful merge sets `changed = true`, `break outer`s, splices the array, and restarts the entire double loop from i=0. With k collinear-overlapping segments requiring merges, this is up to O(k) restarts × O(n²) scan each = O(n³) in the adversarial collinear case (which is exactly the case this code exists to handle — terrain edges overlapping region top edges). The `break outer` + `splice` + full restart is the costly pattern; the pairwise body also calls `pointOnSegment` up to 6 times per pair. Called twice per `buildSectionPslg` (line 494 and 499) and once per attempt. As with B-01 it is worker-side, but on a degenerate collinear-heavy PSLG it can dominate mesh prep time.
- **Recommendation:** Accumulate merges in a single pass (union-find over collinear groups, or sort collinear candidates along a shared direction and sweep) instead of restart-on-each-merge; or at minimum do not restart from i=0 (continue scanning and do a second pass only if anything merged). Fix code.

### [DEF-MESH-B-03] low · Repeated `cleanPolygon(polygon)` recomputation in PSLG region helpers
- **Location:** `src/lib/cpt-app/mesh/section-pslg.js` — `horizontalIntervalsInPolygon:381`, `polygonCentroid:409`, `pointToPolygonBoundaryDistance:428`, `bestInteriorPointForPolygon:438`, all re-call `cleanPolygon`; `soil-regions.js pointInPolygonHalfOpen:219` also calls `cleanPolygon` on every invocation
- **Category:** B — Performance
- **Confidence:** confirmed
- **Analysis:** `bestInteriorPointForPolygon` cleans the polygon once (line 438) then calls `horizontalIntervalsInPolygon` (which cleans again, line 381) for 7 fractions and `pointToPolygonBoundaryDistance` (cleans again, line 428) for every candidate, and each `tryCandidate` calls `pointInPolygonHalfOpen` which cleans yet again per call. `cleanPolygon` allocates a new array, runs a dist-filter loop, computes signed area, and may reverse. For a region with m vertices probed against c candidates this is O(m·c) redundant cleaning per region per attempt. Region seed-point selection runs for every region on every meshing attempt. Not a correctness issue and not on the UI thread, but it is avoidable repeated allocation/work in a per-attempt path.
- **Recommendation:** Clean each polygon once at the top of `buildRegionList`/`bestInteriorPointForPolygon` and pass the already-cleaned point array down (the inner helpers already accept points and re-clean defensively; an internal "assume-clean" variant would remove the duplication). Fix code.

### [DEF-MESH-C-01] high · `T6_mesh_v1.md` documents an incompatible (superseded) node ordering and shape functions vs the shipped code
- **Location:** Doc `docs/deformation/T6_mesh_v1.md:329-372` (ordering `[v0,v1,v2,m01,m12,m20]`, `N4=4L1L2, N5=4L2L3, N6=4L3L1`) and §3.6 Gauss rule; Code `src/lib/cpt-app/deformation/element-t6.js:18-27, 61-67` and `src/lib/cpt-app/mesh/section-mesh.js:124-129, 199-201`
- **Category:** C — Doc vs Code
- **Confidence:** confirmed
- **Analysis:**
  (1) **Doc v1 says:** the recommended strategy is an *app-owned T3→T6 upgrade* (not Triangle `o2`), with node order `0..5 = [v1, v2, v3, m(0-1), m(1-2), m(2-0)]` and shape functions `N4=4·L1·L2`, `N5=4·L2·L3`, `N6=4·L3·L1` (midpoint *between* corners k,k+1), and the orientation flip "is not needed because mid nodes are created after the corner orientation is normalized" (§2.4).
  (2) **Code does:** native Triangle `o2` (`triangleSwitchesForAttempt` adds `o2`, mesh.js:401), with order `[v1,v2,v3,m23,m31,m12]` (midpoint *opposite* corner k), shape functions `N4=4·L2·L3, N5=4·L3·L1, N6=4·L1·L2` (element-t6.js:23-25), gradients written for the opposite-corner convention (element-t6.js:61-67), an *explicit* orientation flip that reorders midpoints `element = [old[0],old[2],old[1],old[3],old[5],old[4]]` (section-mesh.js:320), and `addT6ElementEdges` keyed as `m23↔(n2,n3), m31↔(n3,n1), m12↔(n1,n2)` (section-mesh.js:124-129).
  (3) **Which is correct:** Both ordering conventions are internally self-consistent *if applied uniformly*. The code matches the *newer* `T6_mesh.md` (§1.1, §3.3.1) exactly and is internally consistent end-to-end (shape fns, B, edge map, flip, validation, kernel dispatch). The shipped path is the correct one; `T6_mesh_v1.md`'s convention is mathematically valid only for the app-owned-upgrade strategy that was *not* adopted. Mixing them — e.g. a maintainer porting a helper from v1 (the `N4=4L1L2` block, or the v1 traction DOF list `[2n1,2n1+1,2nMid,2nMid+1,2n2,2n2+1]` at v1:526 which differs from the shipped `[n1,n2,nMid]` order at solver.js:6639) into the shipped opposite-corner code — silently corrupts the element. The v1 doc itself does flag both orderings and even gives the correct `o2` flip `[v0,v2,v1,m20,m12,m01]` (v1:256-262) as an "if you use native o2" aside, but its primary prose and code blocks all assume the m01/m12/m20 adjacent-corner convention.
  (4) **Fix direction:** Fix doc. Mark `T6_mesh_v1.md` as **superseded / historical** at the top, pointing to `T6_mesh.md` as the implemented spec, and add a one-line warning that the shipped code uses native Triangle `o2` opposite-corner ordering, so v1's node/shape-function/traction conventions must not be copied. Do not change code.

### [DEF-MESH-C-02] medium · Doc T6_mesh.md §3.3 / §3.3.1 describes a simpler midnode lookup than the code; code adds an undocumented geometric-midpoint fallback
- **Location:** Doc `docs/deformation/T6_mesh.md:203-209` ("`buildConstraintEdges()` can set `nMid = edgeMidNodeByKey.get(edgeKey(n1,n2))`; if missing, fail") and §12.2 "Missing `nMid` should be a hard meshing error"; Code `src/lib/cpt-app/mesh/section-mesh.js:228-250` and `131-177, 376`
- **Category:** C — Doc vs Code
- **Confidence:** confirmed
- **Analysis:**
  (1) **Doc says:** the corner-pair map is the single source; a missing `nMid` for a constrained T6 edge is an unconditional hard error.
  (2) **Code does:** it first tries the corner-pair `edgeMidNodeByKey`, and *if that misses* it falls back to `lookupMidpointNodeId` — a coordinate-keyed geometric search of the full node list for a node at the edge geometric midpoint (with a 3×3 quantization-neighborhood probe and a 5e-6 m verification), incrementing `diagnostics.recoveredMidNodeCount`, and only throws if *both* fail (section-mesh.js:246-250). The fallback exists because both triangles adjacent to a constrained edge can legitimately be dropped (sliver filter / centroid-outside-polygon on sloping terrain), which would leave the corner-pair map without that edge even though Triangle did emit the midpoint node. This is a genuine robustness improvement over the doc.
  (3) **Which is correct:** The *code* is scientifically/operationally correct and safer — Triangle in `o2` mode places exactly one node at every edge midpoint, so the geometric lookup is canonical and self-validating (each recovered midnode is checked to 5e-6 m at line 173/190). The doc's "fail hard on first map miss" would spuriously reject valid meshes on sloping terrain. The recovery is explicitly NOT a correctness compromise (each result is geometrically verified).
  (4) **Fix direction:** Fix doc. Update `T6_mesh.md` §3.3/§3.4/§12.2 to document the two-stage lookup (corner-pair map → geometric-midpoint fallback → hard error) and the `t6RecoveredMidNodes` diagnostic, so the documented invariant matches the shipped, more-robust behavior. Code is correct.

### [DEF-MESH-C-03] medium · Doc T6_mesh.md prescribes element-averaged stress / one material point per element for results; code uses per-Gauss-point material points
- **Location:** Doc `docs/deformation/T6_mesh.md:718-741` (§7.2 "ship element-averaged stress/plasticity results", "keep one value per parent element"); Code `src/lib/cpt-app/deformation/solver.js:2324-2335` (one material point per Gauss point: `materialPointIndex: globalIndex`, 3 per T6 element) consistent with `T6_mesh_v1.md` §5.4 / Risk 1
- **Category:** C — Doc vs Code
- **Confidence:** confirmed (mesh-layer scope: confirms `numGaussPoints`/integration-point plumbing originates in the mesh→cache layer this audit covers)
- **Analysis:**
  (1) **Doc T6_mesh.md says:** for first delivery, carry one element-averaged stress/plasticity result per parent element (§7.2), and §5.1 frames per-Gauss material points as the integration-point storage. The two docs disagree with each other: `T6_mesh_v1.md` Risk 1 explicitly forbids one centroid material point for T6 plasticity.
  (2) **Code does:** `buildDeformationElementCaches` allocates `kernel.numGaussPoints` integration points per element each with its own flat `materialPointIndex` (3 per T6 element), and the kernel integrates true per-Gauss tangents/stresses (element-t6.js stiffness/internal-force loop over `GAUSS_T6_3PT`). So the constitutive state IS per Gauss point; only the *reported* element result may be an average.
  (3) **Which is correct:** Per-Gauss-point material state (code) is scientifically required for an LST with non-associated MC plasticity — strain varies linearly within the element, so a single centroid material point would erase the element's main benefit and give inconsistent yielding (exactly `T6_mesh_v1.md` Risk 1). The code is correct.
  (4) **Fix direction:** Fix doc. `T6_mesh.md` §5.1/§7.2 wording ("one value per parent element") should clarify that this refers only to the *post-processing display* aggregation, not to the constitutive storage, which is per Gauss point. No code change.

## Notes / limitations of this audit pass
- I read the three target source files and both paired docs in full, and cross-referenced the mesh-consuming code (element-t6.js, element-t3.js, element-kernel.js, the constraint/traction/support and element-cache regions of solver.js, triangle-runtime.js, boundary.js, soil-regions.js, wall-geometry.js). I did not exhaustively read all 8000+ lines of solver.js; the consumer regions audited are those that touch `mesh.elements`, `constraintEdges`/`nodeIds`/`nMid`, `elementType`, `numGaussPoints`, `ndofTotal`, and edge-traction/support assembly.
- I independently verified the two highest-confidence correctness-relevant claims: (a) the orientation flip `[old[0],old[2],old[1],old[3],old[5],old[4]]` is geometrically consistent with the `o2` opposite-corner convention and is confirmed by `validateT6Element`'s midpoint checks; (b) the T6 edge-traction kernel output order `[n1,n2,nMid]` matches the solver's scatter DOF list (solver.js:6639) and the support builder includes `nMid` via `edge.nodeIds`. Both passed.
- I did NOT run the Triangle WASM module to empirically confirm the `o2` midpoint ordering on this exact build; the ordering is asserted by the doc, encoded consistently in code, and guarded at runtime by `validateT6Element` (which would throw on any mismatch). If a second pass is desired, the cheapest hard check is to run `scripts/verify_deformation_phase_1.mjs` Case 0t6b (linear-strain patch test) which is the discriminating test for midpoint ordering correctness.
- The Gauss-rule weights (`w=1/6` with `detJ=2A` ⇒ `A/3` per point) were verified by hand to integrate constants and the consistent body force exactly (Σ = A, midpoint gravity share A·γ/3), matching the verify-script assertions.
- Performance findings (B-01, B-02, B-03) are confirmed as the stated algorithmic shapes; their *real-world* severity depends on typical section/region/load counts which I did not benchmark — they run on the worker thread and do not block the UI.
