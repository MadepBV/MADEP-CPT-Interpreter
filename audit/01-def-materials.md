## Overview
This is a mature, carefully-built constitutive subsystem. The Mohr-Coulomb implementation is the *exact* multisurface principal-stress return-mapping of the Clausen/Sloan family (face/edge/apex + tension cut-off), in a consistent compression-positive internal convention with a tension-positive external (FE) convention, work-conjugate engineering-Voigt gradients, stress-scaled tolerances, and a smoothed Drucker-Prager fallback. The core mathematics — yield/potential surfaces, sign conventions, apex location `−c·cotφ`, tension cut-off `T3 = −σ'₃ − σ_t`, the principal-space coupling solve, and the consistent algorithmic tangent — were cross-checked against MC_pl.md and the governing equations and are scientifically correct. I found **no critical or high correctness bug** in the yield surfaces, return mapping, or tangent. The defects are: a few diagnostic computations that are vacuous or read a non-existent field (so they silently report 0/zero-residual and could mask an inadmissible fallback/plane-strain state), a doc-vs-code default mismatch (`rShear`), a missing ψ≤φ guard, and some dead exports. **Hardening Soil is NOT implemented in JS** — it lives entirely in C++/WASM (`material_hs.hpp`); the JS side only plumbs HS parameters in `material.js`. The paired HS Simo-Hughes doc therefore documents the C++ path, not this JS subsystem.

## Findings

### [DEF-MATERIALS-A-01] medium · Smooth-fallback `yieldResidual` reads non-existent `.F` field → always reports 0
- **Location:** `src/lib/cpt-app/deformation/material-models.js:2330` (`solveLocalMcFallbackTrustRegion`); propagates to `exactYieldFinal` at `material-models.js:3162`
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `evaluateExactMcSurfaceValuesFromStress(...)` returns `{ principal, values }`, where the per-surface residuals live in `exactCurrent.values.{F12,F13,F23,T3}`. Line 2330 computes `yieldResidual: Math.max(Number(exactCurrent?.F) || 0, 0)`. There is no `.F` on that object, so `Number(exactCurrent?.F)` is `NaN`, coerced to `0`. The smooth-fallback return therefore *always* reports `yieldResidual = 0`. This is precisely the value the same function computes correctly two lines later (`branchAcceptanceResidual` at line 2343 = `Math.max(...Object.values(exactValues).map(...), 0)`). The smooth Drucker-Prager fallback does NOT enforce exact MC face/edge closure (it converges on the smoothed surface only), so its true exact-MC residual is generally nonzero — but it is reported as zero, then surfaced as `exactYieldFinal` in the mc-plastic diagnostics record (line 3162). A reviewer reading the run record cannot tell that the fallback left a genuinely inadmissible exact-MC stress. Not used for convergence gating (the fallback always returns `converged:true`), so this is diagnostic-only, but it is a load-bearing diagnostic in engineering-critical software.
- **Recommendation:** Replace line 2330 with the same max-over-`exactValues` expression already used at line 2343 (`Math.max(...Object.values(exactValues).map((v) => Number(v) || 0), 0)`).

### [DEF-MATERIALS-A-02] medium · `recoveryResidual6` is identically zero by construction (vacuous plane-strain diagnostic)
- **Location:** `src/lib/cpt-app/deformation/material-models.js:1520-1523`; surfaced at `material-models.js:1772-1773` and `3174-3175`
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `plasticStrainIncrement6` (line 1515) is defined as `plasticIncrementFromStressCorrection(stressTrial6, stressReturn6, materialParameters)`. `recoveryResidual6` (line 1520) is `subtractVector6(plasticIncrementFromStressCorrection(stressTrial6, stressReturn6, materialParameters), plasticStrainIncrement6)` — i.e. the *same* deterministic pure-function call minus itself. It is therefore identically `[0,0,0,0,0,0]` for every Gauss point on every iteration. Consequently `recoveryResidualNorm` (line 1772) and `planeStrainRecoveryResidualZz` (line 1773), exposed in the mc-plastic diagnostics (`recoveryResidualNorm`, `planeStrainRecoveryResidualZz` at lines 3174-3175), are *always* 0. The evident intent was to verify plane-strain plastic consistency by comparing the elastic-strain-from-stress-difference against an independently-computed flow-rule increment `Σλ·m_principal` (mapped back to Voigt) — measuring the ε_zz recovery error a plane-strain corrector can incur. As written, the check is vacuous and gives false confidence that plane-strain plastic recovery is exact.
- **Recommendation:** Compute one side from the actual plastic-multiplier flow (`Σ λ_q · m6_q` from the accepted active surfaces) and the other from `elasticStrainFromStressIncrement(σ_trial − σ_return)`, then subtract. Or remove the diagnostic if no independent check is intended.

### [DEF-MATERIALS-A-03] low · No ψ ≤ φ' enforcement in `prepareMechanicalMaterial`
- **Location:** `src/lib/cpt-app/deformation/material.js:101` (`psiEffDeg: Math.max(... , 0)`); consumed by `exactMcSurfaceParameters` at `material-models.js:580`
- **Category:** A — Implementation
- **Confidence:** confirmed
- **Analysis:** `prepareMechanicalMaterial` clamps the dilation angle only to `[0, +∞)` (and `clampMcAngle` later caps at 89.5°). It never enforces ψ ≤ φ'. MC_pl.md §8.2 states the non-associated flow rule requires ψ ≤ φ' (associated is the limiting case ψ = φ'). With ψ > φ' the plastic potential normal `m = (1−sinψ)P₁ − (1+sinψ)P₃` dilates more than the yield normal, which violates Drucker stability and produces a non-associated tangent with the wrong sign of volumetric coupling; the exact return can still run but the result is physically invalid and can destabilise the global Newton solve. Note the *safety-reduction* path already clamps it correctly (`psiReducedDeg = Math.min(phiReducedDeg, psiReducedUnclampedDeg)`, material.js:176), so the base prepare path is the inconsistent one. Severity is low because it requires a user/UI to supply ψ > φ'.
- **Recommendation:** In `prepareMechanicalMaterial`, set `psiEffDeg = Math.min(Math.max(psi,0), phiEffDeg)` and emit a warning when the input ψ exceeds φ' (mirroring the Poisson-cap warning pattern).

### [DEF-MATERIALS-A-04] low · `addPorePressureToNormalComponents` clamps pore pressure to ≥ 0 (suction silently dropped)
- **Location:** `src/lib/cpt-app/deformation/material-models.js:93-100`
- **Category:** A — Implementation
- **Confidence:** likely
- **Analysis:** `const u0 = Math.max(Number(porePressure) || 0, 0)` floors negative pore pressure (suction) to zero before adding to the normal stress components. For drained effective-stress screening with hydrostatic-or-positive pore pressures this is harmless, and the matching seed path in post.js (`sigmaV0Eff = Math.max(sigmaV0 − u0, 0)`) also assumes u ≥ 0. But this helper (`totalStress6ToEffectiveStress6`) is a general exported converter; if a caller ever passes negative seepage pore pressure (capillary suction above the phreatic line), the conversion silently ignores it, overstating compression. Severity low because (a) this specific export is currently unused (see DEF-MATERIALS-D-01) and (b) the dominant seepage path returns u ≥ 0. Flagged for the general-converter contract.
- **Recommendation:** If suction is ever in scope, drop the `Math.max(...,0)` here and handle the sign at the physics layer; otherwise document the ≥0 assumption on the export.

### [DEF-MATERIALS-B-01] low · Per-Gauss-point return mapping allocates heavily (arrays-of-arrays in hot loop)
- **Location:** `src/lib/cpt-app/deformation/material-models.js` throughout the exact-MC path — e.g. `solveExactMcCandidateBranch` (1424-1777), `computeExactElastoplasticTangent` (854-971), `buildExactMcSurfaces` (686-745), `zeroMatrix6`/`cloneMatrix6`/`outerProduct6` helpers
- **Category:** B — Performance
- **Confidence:** confirmed
- **Analysis:** The exact return runs once per Gauss point per Newton iteration. Each call allocates many short-lived `Array.from`/array-literal structures: 6×6 and 3×3 matrices (`zeroMatrix6`, `cloneMatrix6`, `symmetrizeMatrix6`, `outerProduct6`), surface objects with fresh `n6`/`m6` (`buildExactMcSurfaces` rebuilt for both trial and representative projectors per candidate branch), candidate-branch retries, and the full tangent rebuild via 6 column solves. For a mesh with thousands of integration points × tens of nonlinear iterations × multiple load steps this is a large GC churn / main-thread cost. This is the *reference* JS implementation (the production hot path is the C++/WASM mirror per `math_js_mirror.hpp`), so the impact on shipped runs is limited, but the JS path is still used for seed projection (`seedMaterialPointStateFromEffectiveStress6` → `solveExactMcActiveSetReturn`) and parity verifiers. No leak (all transient), only allocation pressure.
- **Recommendation:** If the JS path is ever used for full solves, hoist scratch buffers (preallocated 6-vectors / 6×6 / 3×3) and avoid rebuilding surface bundles per candidate. Low priority given WASM is the production path.

### [DEF-MATERIALS-C-01] medium · `rShear` default is 0.25 in code, but ML_pl_fix.md mandates 0.05 (theory-aligned)
- **Location:** Code: `src/lib/cpt-app/deformation/material.js:107`, `material-models.js:2923`, `stage6-bishop.js:2704`. Doc: `docs/deformation/ML_pl_fix.md:272, 278, 501, 604`
- **Category:** C — Doc vs Code
- **Confidence:** confirmed
- **Analysis:** (1) The doc (ML_pl_fix.md §5.3.1, §7 Phase A item 5, §9.1 acceptance) states the Release-A correctness fix sets `rShear = 0.05`, inside the intended first-use range `0.02 ≤ rShear ≤ 0.10`, and the acceptance criterion is "default rShear … theory-aligned". MC_pl.md §9.2 likewise recommends `r = 0.02–0.10`. (2) The code defaults `rShear` to **0.25** in all three places (`Math.max(Number(material?.rShear) || 0.25, 1e-3)`). (3) Scientifically, the doc/MC_pl range is the correct intent: 0.25 is far softer-than-elastic but stiffer than the recommended pseudo-plastic residual, so it understates how much the MC-active zone yields and shifts displacement/utilisation results vs. the documented model. This is a screening (reduced-stiffness) model, not the recommended physical route, so the engineering impact is bounded — hence medium not high. (4) **Fix direction:** change the code default to 0.05 to match the spec, OR (if 0.25 is a deliberate, validated screening choice) update ML_pl_fix.md and MC_pl.md to record 0.25 as the shipped default with rationale. The current state is a genuine contradiction the doc itself calls a release-blocking acceptance item.
- **Recommendation:** Reconcile to a single documented value (prefer 0.05 per spec, or amend both docs if 0.25 is intentional).

### [DEF-MATERIALS-C-02] low · MC.md (v1 spec) describes an elastic screening tool; code is a full elastoplastic return-mapping solver
- **Location:** Doc `docs/deformation/MC.md` (esp. §3 "What It Explicitly Does Not Do": "no return mapping / plastic correction"; §11.6 `mohrCoulombIndicator`). Code: full exact-plastic implementation in `material-models.js` (`createMCPlasticMaterial`, `solveExactMcActiveSetReturn`, …)
- **Category:** C — Doc vs Code
- **Confidence:** confirmed
- **Analysis:** (1) MC.md is explicitly the "easy MC route … intentionally not a full elastoplastic Mohr-Coulomb solver", listing "full elastoplastic Mohr-Coulomb", "return mapping / plastic correction", and "dilation-driven plastic strains" as out of scope. (2) The code now implements exactly those: a true `mc-plastic` plugin with exact multisurface return mapping, non-associated dilation, tension cut-off, and algorithmic tangent. MC_pl.md (the plastic spec) is the correct pairing and matches the code well. ## Notes / limitations of this audit pass
- I verified the MC mathematics directly against MC_pl.md and first principles: compression-positive convention and the `−sigma6` adapter; surfaces F12/F13/F23 with normals `(1∓sinφ)`; potential with sinψ; tension `T3 = −σ'₃ − σ_t`; apex at `s = −c·cotφ` (confirmed by setting F13=0 at hydrostatic, so `exactMcHydrostaticApexStress = −c/tanφ` is correct); the principal-space coupling solve `nᵀ D_n m`; the consistent tangent `D_e − (D_e m)(D_e n)ᵀ/(nᵀ D_e m)`; and the equivalent plastic strain `sqrt((2/3) ε_dev:ε_dev)` with the weighted W=diag(1,1,1,½,½,½) contraction. All were correct.
- I did NOT exhaustively trace every branch of the edge/apex/tension active-set candidate ordering (`solveExactMcActiveSetReturn`, lines 1779-2059) for completeness against all Clausen corner cases, nor re-derive `principalRepresentationDerivativeForBranch` for every repeated-eigenvalue case; those passed spot checks (lower/upper repeated and triple-apex averaging matrices are the standard ½/⅓ forms) but a dedicated single-material-point return-mapping test harness (which MC_pl.md §21 item 9 recommends) would give stronger assurance than static reading.
- The flat-K0 seed sets σ'_zz = σ'_h0 = K0·σ'_v0 (post.js:104-110), which is a defensible at-rest out-of-plane assumption and does NOT use the `ν(σ'_xx+σ'_yy)` lift that ML_pl_fix.md §2.2 warned about; the legacy `planeStrainCompressionPositiveStress2DToStress6` lift (material-models.js:2436-2449) is only reached on the non-array fallback seed path. I judged this consistent, not a bug.
- HS constitutive correctness (Simo-Hughes) was explicitly out of scope here because it has no JS implementation; it must be audited in the C++/WASM subsystem.
- The smoothed Drucker-Prager fallback uses the compression-meridian match `α = 6sinφ/(3−sinφ)`, `k = 6c·cosφ/(3−sinφ)`; this is a standard MC approximation, intentionally not exact MC, and is only invoked when the exact return fails — correct by design.
