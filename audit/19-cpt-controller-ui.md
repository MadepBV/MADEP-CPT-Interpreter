# Audit — Legacy controller orchestration, state & UI wiring
**Subsystem key:** cpt-controller-ui
**Files reviewed:** /Users/mathiasdepelsmaeker/Projects/madep-cp/src/lib/cpt-app/legacy-controller.js, /Users/mathiasdepelsmaeker/Projects/madep-cp/src/routes/+page.svelte (caller of `initLegacyController`), /Users/mathiasdepelsmaeker/Projects/madep-cp/src/lib/cpt-app/stage6-bishop.js (only `buildBishopModelFromStageLayers`, to gauge redraw cost)
**Finding counts:** critical=0 high=2 medium=4 low=5 info=2  |  A=1 B=6 C=0 D=6  |  total=13

## Overview
The 18.5k-line controller is the orchestration layer of the monolith: global mutable `PROJECT`/`S` state, a singleton-per-kind worker pool (Bishop search / seepage / deformation), Chart.js lifecycle, canvas redraw, and a very large set of inline-`onclick` UI handlers exported onto `window`. Worker lifecycle is mostly disciplined (run-id guards, terminate-on-error, singleton ensure). The dominant architectural smell is the leaky module/component boundary: `initLegacyController()` advertises a teardown function to `+page.svelte`'s `onMount` cleanup but returns a no-op, so `document`/`window` listeners and the polluted `window.*` API are never removed. There are several confirmed resource leaks (Chart.js instances on tuning re-render, blob URL on SVG export, deformation worker not stopped on CPT switch), one genuine UI-wiring bug (`stage6BishopSetSelectedRegionCoarseness` invoked from inline HTML but never exported to `window`), redundant per-frame model rebuilds in the canvas hot path, and a handful of orphaned helpers plus a large feature-flag-disabled (Hardening-Soil) code surface. None of the controller-layer findings are numerically catastrophic on their own, but several degrade long-session memory and interactivity.

## Findings

### [CPT-CONTROLLER-UI-A-01] medium · Inline handler calls `stage6BishopSetSelectedRegionCoarseness`, which is never exported to `window` (ReferenceError on edit)
- **Location:** `legacy-controller.js:6874` (definition), inline handlers at `9348`, `16204`, `16614`–`16615`; export block `18275`–`18442` (function absent); sibling `stage6BishopSetSelectedRegionMaterial` exported at `18389`
- **Category:** A — Implementation (broken UI wiring)
- **Confidence:** confirmed
- **Analysis:** The custom-region coarseness input is rendered with `onchange="stage6BishopSetSelectedRegionCoarseness(this.value)"` and an Enter-key handler `onkeydown="if(event.key === 'Enter'){ ... stage6BishopSetSelectedRegionCoarseness(this.value); ... }"`. Inline DOM event handlers resolve identifiers against the **global** scope, but `initLegacyController` only assigns the members of `legacyApi` onto `window` (`Object.assign(window, legacyApi)` at `18446`). The function `stage6BishopSetSelectedRegionCoarseness` is **not** a member of `legacyApi` (verified: a whole-repo `grep` finds it only as the definition, one internal call from the commit wrapper, and the three inline-handler sites — never in the export block, never `window.x = ...`). Its sibling `stage6BishopSetSelectedRegionMaterial` *is* exported (`18389`), which is what makes the omission a clear oversight. At runtime, changing the selected polygon's coarseness or pressing Enter in that field throws `ReferenceError: stage6BishopSetSelectedRegionCoarseness is not defined`, so the intended immediate `renderStage6()` (which updates the "effective local target area" help text shown live) does not fire. The data is not permanently lost only because `stage6BishopCommitPendingSelectedRegionCoarseness()` reads the input by id (`st6-bishop-selected-region-coarseness`) just before each solver run (`8153`, `8213`, `8282`) — i.e. the value is recovered on the next run, masking the bug. Severity medium rather than high because of that fallback.
- **Recommendation:** Add `stage6BishopSetSelectedRegionCoarseness` (and arguably the `Commit...` wrapper) to the `legacyApi` export block next to `stage6BishopSetSelectedRegionMaterial`. Alternatively, change the inline handlers to call the already-exported commit wrapper. Verify in a browser that editing coarseness updates the help text live without a console error.

### [CPT-CONTROLLER-UI-B-01] high · `initLegacyController` returns a no-op teardown; `document`/`window` listeners and `window.*` API are never removed
- **Location:** `legacy-controller.js:18444`–`18455` (returns `()=>{}`), `bindDropzone` `1955`–`1966`, hashchange `18451`, top-level `.si` binding `1142`–`1146`; consumer `+page.svelte:27`–`41`
- **Category:** B — Memory leak (listeners/closures never removed)
- **Confidence:** confirmed
- **Analysis:** `+page.svelte`'s `onMount` does `destroy = mod.initLegacyController?.()` and returns `() => { ...; destroy?.(); }` as the Svelte cleanup. `initLegacyController` performs side effects — `Object.assign(window, legacyApi)` (pollutes `window` with ~165 functions/refs incl. `PROJECT`), `bindDropzone()` (three `document.addEventListener` for `dragover`/`dragleave`/`drop`, each closing over a captured `dz` node), and `window.addEventListener('hashchange', stage6BishopHandleHashChange)` — but then `return ()=>{}` (a no-op). So the destroy function the component faithfully calls does nothing. File-level the controller has 11 `addEventListener` and **0** `removeEventListener`. The `__legacyControllerInitialized` guard prevents re-entry, so on a single page load this is benign; but on Vite HMR or any unmount/remount of the page component, the old `document`/`window` listeners and the entire retained-closure graph (each dropzone listener pins a `dz` DOM node and, transitively, `importGEFFiles`→`PROJECT`) survive, plus stale `window.*` bindings remain. The top-level `.si` click binding at `1142` (module-scope, outside any function) is likewise unremovable. This is the central architectural-health issue of the subsystem: the teardown contract with the Svelte host is advertised but unfulfilled.
- **Recommendation:** Have `initLegacyController` collect its listeners (store handler refs) and return a real teardown that calls `removeEventListener` for the dropzone (`document`) and hashchange (`window`) handlers, clears `__legacyControllerInitialized`/`__legacyControllerHashBound`, terminates any live workers, and optionally deletes the keys it added to `window`. Move the top-level `.si` binding into `initLegacyController` so it is bound/unbound with the lifecycle. Use `AbortController`+`{signal}` to make teardown trivial.

### [CPT-CONTROLLER-UI-B-02] high · Tuning charts (`tChart*`) are leaked: `renderTuning` replaces canvases via `innerHTML` without `.destroy()`
- **Location:** `legacy-controller.js:3840`–`3848` (`renderTuning` sets `el.innerHTML = ...`), `buildTuningCharts` `3988`–`4047` (creates `new Chart` stored on `canvas._chartRef`), guarded only by `canvas._built`
- **Category:** B — Memory leak (Chart.js instances + internal listeners retained)
- **Confidence:** confirmed
- **Analysis:** `renderTuning` rebuilds the whole tuning area with `el.innerHTML = S.tuning.map(...).join('')`, discarding the previous `<canvas id="tChart{i}">`/`tChart{i}d` nodes. Each of those canvases holds a live Chart.js instance on `_chartRef` (`4010`, `4043`). Chart.js registers every instance in its module-global `Chart.instances` registry and attaches its own resize/DOM listeners; replacing the canvas DOM node without calling `chart.destroy()` orphans the instance — it is **not** garbage-collected because the registry keeps a strong reference. Every "Run fitting" / tuning re-render (and there can be many per layer-tuning session) leaks N×2 chart instances. The codebase clearly knows the correct pattern: `stage6DestroyChart(id)` (`16831`–`16834`) calls `._chartRef.destroy()` before recreating, and it is used consistently for all Stage-6, pile, settlement, dewatering, beam, line-probe charts. The tuning charts are the one family that bypasses it. (The main qc/fs/rf charts are destroyed in `selectCpt` via `Object.values(S.charts).forEach(c=>c.destroy())`, so they are not affected.)
- **Recommendation:** Before `renderTuning` overwrites `tuningArea.innerHTML`, iterate existing `tChart*`/`tChart*d` canvases and call `_chartRef?.destroy()` (mirror `stage6DestroyChart`). Or route tuning chart creation through `stage6DestroyChart`-style destroy-then-create helpers.

### [CPT-CONTROLLER-UI-B-03] medium · `selectCpt` stops the search & seepage workers but NOT the deformation worker on CPT switch
- **Location:** `legacy-controller.js:147`–`160` (`selectCpt` calls `stage6BishopStopSearch(true)` `149` and `stage6BishopStopSeepage(true)` `150`, no `stage6BishopStopDeformation`); `stage6BishopStopDeformation` defined `7850`; the deformation worker is a module-level singleton `stage6BishopDeformationWorker` `93`
- **Category:** B — Performance / orphaned worker (resource not released)
- **Confidence:** confirmed
- **Analysis:** When the user switches the active CPT, `selectCpt` terminates the Bishop search and seepage workers but leaves the deformation worker — the heaviest of the three (a full plane-strain T3/T6 FEM solve with possible c-φ reduction continuation) — running. State corruption is avoided: the deformation `onmessage` (`8031`) guards on `payload.runId !== deformation.progress?.runId`, and run-ids are drawn from a monotonic module-global counter (`stage6BishopDeformationRunId`, `8313`) while `progress.runId` is stored per-CPT, so a late result for the previous CPT is correctly dropped. But the worker continues to consume a CPU core and its WASM/JS heap for the full (potentially many-second) solve after the user has moved on, with no way to stop it short of finishing. This is an inconsistency: search and seepage are stopped, deformation is not.
- **Recommendation:** Add `stage6BishopStopDeformation(true)` to `selectCpt` alongside the existing two stop calls (and consider the same in `removeCpt`).

### [CPT-CONTROLLER-UI-B-04] medium · Canvas redraw rebuilds the full Bishop model every frame (`stage6BishopSyncSoilModel` + `buildBishopModelFromStageLayers`) including during pan and search progress
- **Location:** `legacy-controller.js:11277`–`11279` inside `stage6BishopDrawCanvas`; hot callers: pan in `stage6BishopPointerMove` `11110`, search progress `onmessage` `7919`; `buildBishopModelFromStageLayers` in `stage6-bishop.js:2793`
- **Category:** B — Redundant recompute in hot path / per-frame allocation
- **Confidence:** confirmed
- **Analysis:** `stage6BishopDrawCanvas` unconditionally calls `stage6BishopSyncSoilModel()` then `buildBishopModelFromStageLayers(stage6WorkingLayers(), bishop)` on every invocation, and caches the result to `S.stage6Cache.bishopModel` only to recompute it next frame. `stage6BishopDrawCanvas` is called from ~11 sites, including (a) pan drag at pointer-move frequency (`11110`) and (b) every Bishop search progress message (`7919`), which can fire many times per second with preview-circle updates. `buildBishopModelFromStageLayers` sorts terrain vertices, calls `importBishopMaterialsFromLayers` (a second time — `stage6BishopSyncSoilModel` already imported them moments earlier under a layer-signature guard at `6667`), builds per-layer bands, and constructs auto-region polygons (`buildCptAutoRegions`) and normalizes custom-region polygons (`stage6-bishop.js:2807`–`2826`+). During panning or a running search the layers/terrain are unchanged, so this geometry rebuild + duplicate material import is pure redundant work and per-frame garbage. Cost is bounded by layer count (typically <20), so it is not catastrophic, but it is avoidable churn in the most performance-sensitive path.
- **Recommendation:** Cache the built model keyed by a cheap signature (layer signature + terrain hash + custom-region revision + strengthSet) and reuse it in `stage6BishopDrawCanvas`; only rebuild when the signature changes. Pan/zoom redraws (which change only the viewport transform) should never trigger a model rebuild.

### [CPT-CONTROLLER-UI-B-05] low · `removeCpt` destroys the wrong CPT's charts and leaks the removed CPT's Chart.js instances
- **Location:** `legacy-controller.js:268`–`278` (`removeCpt`), interacting with chart-destroy in `selectCpt` `155`–`157`
- **Category:** B — Memory leak (Chart.js instances of removed CPT not destroyed)
- **Confidence:** likely
- **Analysis:** `removeCpt` splices the CPT at `idx` out of `PROJECT.cpts` (`271`), then sets `S = PROJECT.cpts[newActive]` (`275`) and calls `selectCpt(newActive)` (`277`). `selectCpt`'s chart-destroy step (`156`) runs `Object.values(S.charts).forEach(c=>c.destroy())` on **`S`**, which by that point is already the *new* active CPT — so it destroys (then immediately rebuilds) the new CPT's charts, while the **removed** CPT object (and its `.charts` Chart.js instances) has already been dropped from `PROJECT.cpts` without ever being destroyed. Those instances stay alive via Chart.js's global registry until something else reuses the canvas. Because all CPTs share the same DOM canvases (`cQc`/`cFs`/`cRf`) and `selectCpt` rebuilds `chartArea` `innerHTML`, the practical leak is small/transient, hence low severity — but the cleanup targets the wrong object.
- **Recommendation:** Destroy the removed CPT's charts *before* splicing (`PROJECT.cpts[idx].charts` then `delete`), or have `removeCpt` not pre-assign `S` and let `selectCpt` handle the (correct) target. Also drop the redundant `renderBanner()` at `276` (immediately repeated inside `selectCpt`).

### [CPT-CONTROLLER-UI-B-06] low · `exportSectionSVG` never revokes its `createObjectURL` blob URL
- **Location:** `legacy-controller.js:908`–`916`
- **Category:** B — Memory leak (object URL retained)
- **Confidence:** confirmed
- **Analysis:** `a.href = URL.createObjectURL(blob)` (`913`) followed by `a.click()` with no `URL.revokeObjectURL`. The blob (full section SVG markup) is pinned for the lifetime of the document on every export. File-level there is 1 `createObjectURL` and 0 `revokeObjectURL`. Severity low: triggered only by an explicit user export and the blobs are modest, but it is a textbook avoidable leak (the other three exporters — CSV/Plaxis — use `data:` URIs and have no such issue, so this one is the outlier).
- **Recommendation:** After `a.click()`, call `URL.revokeObjectURL(a.href)` (e.g. on a `setTimeout(...,0)` or `requestAnimationFrame` to be safe across browsers).

### [CPT-CONTROLLER-UI-B-07] low · `initCharts` retries forever via `setTimeout` if the CDN Chart.js never loads
- **Location:** `legacy-controller.js:1768`–`1777` (`if(typeof Chart==='undefined'){ setTimeout(()=>initCharts(), 120); return; }`); Chart.js is loaded from a remote CDN in `+page.svelte:66`
- **Category:** B — Unbounded retry loop / main-thread wakeups
- **Confidence:** confirmed
- **Analysis:** Because Chart.js is injected as a third-party `<script src="https://cdnjs.cloudflare.com/...">` (not a bundled import), `Chart` may be permanently `undefined` if the CDN is blocked/offline. `initCharts` then re-schedules itself every 120 ms indefinitely, a perpetual timer with no attempt cap and no user-visible failure. Low severity (only on CDN failure) but it is an unbounded background loop with no escape hatch.
- **Recommendation:** Cap the retry count (e.g. ~50 attempts ≈ 6 s) and surface a "charting library failed to load" message instead of spinning forever; or bundle Chart.js as a module import so availability is deterministic.

### [CPT-CONTROLLER-UI-D-04] info · `renderStage6()` (and `setStage6Field`) do a full synchronous recompute + `innerHTML` rebuild on every field change
- **Location:** `legacy-controller.js:16774`–`16829` (`renderStage6`), `5148`–`5165` (`setStage6Field` → `renderStage6`); `renderStage6()` is called from 129 sites
- **Category:** D / B — Architectural pattern (full re-render on every interaction)
- **Confidence:** confirmed
- **Analysis:** Each `renderStage6` re-runs the active engineering analysis (`analyzePile` / `analyzeSettlement` / `analyzeDewatering` / `analyzeBeamAndReinforcement` / bearing profile) and then replaces `stage6Area.innerHTML` wholesale, re-binding all inline handlers and rebuilding all Stage-6 charts on the next animation frame. Every `oninput`/`onchange` field edit triggers the full cycle (only `bearing.Df` has a fast path via `refreshStage6BearingPreview`). This is the pervasive, intentional design of the monolith and not a discrete bug, so it is reported as info — but it is the main source of main-thread work per keystroke and the reason the worker-offloaded analyses (Bishop/seepage/deformation) feel responsive while the synchronous ones can jank on large inputs. Captured here for architectural-health completeness; the scroll/details-state preservation machinery (`stage6CaptureScrollState`/`stage6RememberDetailsState`) exists precisely to paper over the destructive full re-render.
- **Recommendation:** Long-term, debounce field-driven re-renders and/or split "recompute analysis" from "re-render DOM" so cheap display tweaks don't re-solve. No immediate change required.

## Notes / limitations of this audit pass
- I confirmed the export-gap (A-01) and listener/worker/chart leaks (B-01..B-06) directly from the code; the *runtime* manifestation of A-01 (a thrown `ReferenceError` in the browser console) was inferred from inline-handler scoping rules, not observed in a live session — a quick manual repro (edit a custom-region coarseness with devtools open) would close the loop.
- The worker run-id race analysis assumes the run-id counters are only ever incremented in this file (verified) and that worker code respects the `runId` echo; I did not re-audit the worker scripts themselves (`stage6-bishop-worker.js`, `seepage/seepage-worker.js`, `deformation/deformation-worker.js`) — those are outside this subsystem.
- Dimension C produced no findings: this subsystem has no tightly-paired docs, and the math/standards docs (`docs/**`, `src/routes/docs/**`) are owned by the classification/constitutive auditors. Inline comments I spot-checked (chart "created once / updated in-place", serial file loading, HS-flag rationale, run-id guards) matched the code.
- Orphan detection (D-02) used `\b`-bounded whole-repo grep; functions reachable *only* via dynamically-built strings other than `on*="name("` handlers (none found here) could in principle be missed, but I cross-checked the inline-handler name set against the `window` export set and only the A-01 gap surfaced.
- Performance findings (B-04) are reasoned from per-call work and call frequency, not from profiling; the absolute cost is layer-count-bounded and modest, so they are correctness/churn observations rather than measured hotspots.
