# NEN 6740 — Reference Spec for a Faithful Implementation

**Purpose:** describe what a *best-available, source-faithful* implementation of
the NEN 6740 CPT classification route should do in this codebase.

This document is intentionally stricter than the current app behaviour. It
describes the implementation we should target if the goal is to match the
published NEN 6740 / D-SHEET-style workflow as closely as practical.

Because the source method is presented graphically and the chart itself is
copyrighted, this document does **not** reproduce the chart geometry. Instead
it specifies the algorithm, the expected behaviours, and the benchmark
requirements needed for a faithful implementation.

---

## Source Hierarchy

For this method the sources do not all play the same role. A faithful
implementation should treat them in this order:

1. **Normative source**
   `NEN 6740:2006` — the governing Dutch standard.
2. **Operational implementation source**
   `Deltares D-SHEET Piling User Manual` — the clearest public description of
   how the NEN stress-dependent CPT interpretation is actually operationalised
   in software.
3. **Public chart reproductions**
   Useful for visual cross-checking of the 14 material areas and their order,
   but not authoritative over the standard or the vendor manual.
4. **This repository**
   Internal comparison material only. Current code is not a source of truth.

If a licensed copy of NEN 6740 and a licensed D-SHEET installation are both
available, D-SHEET should be used as the behavioural benchmark for regression
tests, while the standard remains the normative reference.

---

## What “Perfect” Means Here

A perfect implementation should:

- use the published stress-dependent NEN 6740 route rather than a simplified
  nearest-centre approximation;
- preserve the full 14 material areas during classification and raw layer
  generation;
- apply the documented preprocessing/filtering workflow before classification;
- return `Undetermined` when a point lies outside the diagram or when required
  inputs are missing;
- make every non-normative assumption explicit and benchmark it against
  D-SHEET outputs.

A perfect implementation should **not**:

- classify every raw CPT point directly without the documented filtering;
- force outside-chart points into the nearest named material;
- default a missing friction ratio to an arbitrary constant and continue as if
  the input were valid;
- collapse the 14 NEN materials to broad internal families before raw
  boundary generation;
- treat an app-side regression coefficient as if it were a NEN constant.

## Required Inputs

At minimum the method needs:

| Symbol | Meaning | Unit | Notes |
|---|---|---|---|
| `z` | depth below ground level | m | per CPT sample |
| `qc` | cone resistance | MPa | measured |
| `fs` or `Rf` | sleeve friction or friction ratio | MPa or % | at least one is required |
| `z_w` | phreatic level / groundwater level | m | needed for effective stress |
| `sigma'v0` model | effective stress at depth | kPa | must be documented explicitly |
| `Hmin` | minimal layer thickness / sublayer thickness | m | part of the documented profile-generation workflow |

If only `fs` is available, compute:

```text
Rf = 100 * fs / qc
```

If neither `fs` nor `Rf` is available, the result should be `Undetermined`,
not a guessed material.

## Target Algorithm

### 1. Preprocess the CPT first

The Deltares workflow describes a two-stage filtering step before soil
material interpretation:

1. average the raw CPT data every 3 depth points;
2. divide the depth range into `Hmin` sublayers;
3. compute filtered values per sublayer from the 3-point averages inside that
   sublayer.

For a faithful implementation, classification should run on the **filtered**
series, not on every raw point.

Recommended implementation detail:

- filter `qc` and `fs` first;
- derive `Rf` from the filtered values as `100 * fs_filter / qc_filter`.

This avoids ratio noise and is physically better behaved than filtering `Rf`
directly. If strict D-SHEET equivalence is required, this choice should be
benchmarked against D-SHEET with a licensed reference dataset and adjusted if
needed.

### 2. Compute effective stress explicitly

The stress correction uses the effective overburden stress at the reading
depth. A faithful implementation must therefore make the stress model explicit.

Minimum behaviour:

```text
sigma_v0  = total vertical stress at depth z
u         = hydrostatic pore pressure from the phreatic level
sigma'v0  = max(sigma_v0 - u, 1 kPa)
```

The public sources confirm that the NEN route is stress-dependent, but they do
not fully disclose every preliminary modelling assumption used by vendor
software before the soil profile exists. For that reason:

- the stress model used during Stage 2 must be documented in code and docs;
- if vendor equivalence is the goal, the stress model must be benchmarked
  against D-SHEET and not treated as “obviously known”.

### 3. Apply the NEN stress correction

Use the documented D-SHEET stress-correction form:

```text
qc,NEN = qc * (100 / sigma'v0)^0.67
```

with `sigma'v0` in `kPa` and `qc` in `MPa`.

If `sigma'v0 < 1 kPa`, floor to `1 kPa` before correction. That guard is a
numerical convenience, not a soil-model statement.

### 4. Classify by chart area, not by nearest centre

This is the biggest difference between a convenience implementation and a
faithful one.

The NEN 6740 route is a **14-area semilog chart**. A perfect implementation
should classify a point by **testing membership in the actual chart areas**.

Recommended representation:

- transform to chart coordinates:

```text
x = Rf
y = log10(qc,NEN)
```

- digitise the actual material boundaries from the chart;
- represent each area as a polygon or as an interval between boundary lines in
  `(x, y)` space;
- classify by point-in-polygon or explicit band-membership tests.

Do **not** collapse the chart to:

```text
score = log10(qc,NEN) - k * Rf
```

and then choose the nearest stored centre, except perhaps as a temporary
diagnostic or QA tool. That projection can be useful for analysis because the
bands are visually close to parallel, but it is still an approximation of the
published chart, not the chart itself.

### 4a. Practical digitisation workflow

If we want this app to implement NEN 6740 better than it does today, the chart
should be digitised explicitly and stored as machine-readable geometry.

Recommended workflow:

1. **Use the best source image available**
   Prefer a licensed chart image from the standard or D-SHEET documentation.
   A public thesis reproduction is acceptable for exploratory work, but it
   should not be the final calibration source if a better licensed image is
   available.
2. **Crop only the plotting window**
   Remove page margins, caption text, and surrounding UI so the digitisation is
   tied only to the chart frame.
3. **Calibrate the axes**
   The chart axes are:

   ```text
   x = Rf                      linear, typically 0 to 10 %
   y = log10(qc,NEN)           logarithmic, qc,NEN from 0.01 to 100 MPa
   ```

   Store at least four calibration points:

   - left axis at `Rf = 0`
   - right axis at `Rf = 10`
   - bottom axis at `qc,NEN = 0.01`
   - top axis at `qc,NEN = 100`

   Then convert pixel coordinates `(px, py)` to chart coordinates `(x, y)` by:

   ```text
   x = linear map from px to Rf
   y = linear map from py to log10(qc,NEN)
   ```

   The important part is that the vertical mapping is to `log10(qc,NEN)`, not
   to `qc,NEN` itself.
4. **Trace the boundaries, not just the centres**
   The current implementation stores one representative centre per material.
   The upgraded implementation should instead trace every boundary separating
   neighbouring materials.

   Practical options:

   - trace each boundary as a polyline with manually selected vertices;
   - fit each boundary as a straight line in `(Rf, log10(qc,NEN))` space if the
     source image confirms that the boundary is effectively straight;
   - where needed, allow piecewise-linear boundaries instead of forcing one
     global slope.
5. **Build polygons for the 14 areas**
   Once the separating boundaries are known, derive the actual material areas as
   polygons in chart space.

   This is the most robust storage format for classification because it avoids
   hidden assumptions about slope continuity, extrapolation, and area closure.
6. **Store provenance alongside the geometry**
   The digitised dataset should include:

   - source image name and checksum;
   - calibration points;
   - traced boundary vertices;
   - generated polygons;
   - the mapping from area id to NEN material label and parameter row.

Recommended repo structure:

```text
src/lib/cpt-app/nen6740-areas.json
```

with one entry per material area plus a metadata block for calibration.

### 4b. Recommended classifier from the digitised chart

Once digitised, the classifier should work like this:

1. compute `qc,NEN`;
2. transform to chart coordinates:

```text
x = Rf
y = log10(qc,NEN)
```

3. reject immediately if the point is outside the calibrated chart frame;
4. test point-in-polygon against the 14 stored NEN areas;
5. if exactly one polygon matches, return that material;
6. if none match, return `Undetermined`;
7. if multiple polygons match because the point falls on a shared boundary, use
   a deterministic boundary rule.

Recommended boundary rule:

- assign ownership of each shared edge explicitly when the polygons are built;
- otherwise fall back to a stable published-area order.

The current scalar score can remain in the codebase as a debug metric:

```text
score = log10(qc,NEN) - 0.34 * Rf
```

but it should no longer be the primary classification rule.

### 4c. How to prove the digitised solution is better than today

“Better” should be demonstrated, not assumed.

The digitised implementation should beat the current nearest-centre method on
three fronts:

1. **Source fidelity**
   On manually labelled benchmark points taken directly from the chart, the
   digitised classifier should reproduce the intended material area exactly,
   while the current nearest-centre method will misclassify some near-boundary
   points because it collapses the 2D chart to a 1D score.
2. **Boundary behaviour**
   The digitised classifier should produce fewer incorrect flips near the weak
   transitions, especially around the current area-5/area-6 and adjacent clay /
   loam / sand transitions. This is where the current score model is most
   fragile.
3. **Outside-chart behaviour**
   The digitised classifier should return `Undetermined` outside the diagram.
   The current implementation cannot do this because it always selects the
   nearest stored centre.

Recommended acceptance tests:

- 100% correct on a manually curated set of clear interior points for all 14
  areas;
- deterministic handling of a curated set of boundary points;
- 100% `Undetermined` on a curated set of outside-chart points;
- improved agreement with licensed D-SHEET outputs on benchmark CPT datasets;
- equal or lower disagreement than the current nearest-centre method on every
  benchmark family.

Recommended benchmark design:

- `centre points`: one or more obvious interior points per material;
- `boundary points`: points just above and below each traced boundary;
- `corner points`: points near area ends and clipped regions;
- `outside points`: low-`Rf`, low-`qc,NEN`; high-`Rf`, high-`qc,NEN`; and other
  points outside the published envelope.

For this app specifically, where the input will remain **unsmoothed**, the
benchmark should also include raw-point-style noisy sequences. The goal is not
to imitate D-SHEET filtering, but to prove that the **chart classifier itself**
is more faithful and more stable than the current score-based approximation on
unsmoothed input.

### 5. Return `Undetermined` outside the chart

If the `(Rf, qc,NEN)` point lies outside all digitised NEN areas, the result
should be:

```text
type    = Undetermined
subtype = undetermined
```

This is important. A faithful implementation should not assign a nearest valid
soil when the source method says the point is outside the diagram.

The same rule should apply when required inputs are missing or invalid:

- `qc <= 0`
- no usable `fs` and no usable `Rf`
- impossible or missing groundwater/stress context when the stress-dependent
  route is selected

### 6. Preserve the 14 material labels

The raw classifier should return the actual NEN material, not just a broad
family. The chart labels visible in the public reproductions are:

1. gravel, slightly silty, moderate
2. sand, clean, stiff
3. sand, slightly silty, moderate
4. sand, very silty, loose
5. loam, very sandy, stiff
6. loam, slightly sandy, weak
7. clay, very sandy, stiff
8. clay, slightly sandy, moderate
9. clay, clean, stiff
10. clay, clean, weak
11. clay, organic, moderate
12. clay, organic, weak
13. peat, moderately preloaded, moderate
14. peat, not preloaded, weak

These 14 labels are not just display names. They are the classification output.

### 7. Use the 14 materials for raw boundary generation

For the NEN 6740 route, raw segmentation should use:

```text
segment key = material id / subtype
```

not just the broad internal family (`Sand`, `Clay`, `Peat`, etc.).

Only after the raw material sequence exists should the app apply:

- minimum thickness enforcement;
- similarity-based cleanup;
- any optional family-level simplification.

If two adjacent filtered sublayers classify as different NEN materials, that
should create a raw boundary even when both later map to the same broad family.

### 8. Map each material to its NEN parameter row

The 14 interpreted materials should map to the corresponding parameter row from
the NEN / D-SHEET material table used for this route.

This mapping should be explicit in code:

```text
material id -> label, broad family, gamma, gamma_sat, phi', c', cu
```

Important distinction:

- the **classification route** is the 14-area chart;
- the **parameter mapping** is the associated NEN material table;
- these should be stored separately so the chart logic can be audited without
  mixing it with parameter defaults.

### 9. Keep tie handling narrow and explicit

If a point falls exactly on a digitised boundary, use a deterministic rule such
as:

1. first polygon match in published chart order;
2. or boundary ownership assigned explicitly during digitisation.

But ties should be rare. If ties happen often, the geometry is too coarse or
the classifier has been over-compressed.

## Recommended Data Structures

The implementation should separate three concepts:

1. `NEN6740_AREAS`
   actual chart geometry in `(Rf, log10(qc,NEN))` space
2. `NEN6740_MATERIALS`
   metadata and parameter mapping for each of the 14 materials
3. `NEN6740_BENCHMARKS`
   golden test cases compared against D-SHEET or licensed reference outputs

Suggested shape:

```js
{
  id: 5,
  subtype: 'loam, very sandy, stiff',
  type: 'Sandy clay',
  polygon: [...],
  g: 20,
  gs: 20,
  phi: 35,
  c: 1,
  cu: 0
}
```

If polygons are awkward, store ordered boundary lines instead:

```js
{
  lower: (rf) => ...,
  upper: (rf) => ...
}
```

in `y = log10(qc,NEN)` space. The important thing is that the classifier uses
the **actual area envelopes**, not a nearest-centre shortcut.

## Validation Requirements

A perfect implementation needs stronger validation than “it reproduces its own
stored centres”.

### 1. Golden chart tests

Build a benchmark suite with points:

- clearly inside each of the 14 areas;
- near every boundary;
- on representative low, mid, and high stress levels;
- outside the chart on all sides.

Expected result:

- inside points classify to the intended area;
- boundary cases follow the documented tie rule;
- outside points return `Undetermined`.

### 2. D-SHEET parity tests

For a set of CPTs with known water level and `Hmin`, compare the full output
against licensed D-SHEET results:

- filtered `qc` and `Rf`;
- `qc,NEN`;
- interpreted material per sublayer;
- generated raw boundaries.

This is the key benchmark for any implementation choice the public documents do
not fully specify.

### 3. Regression tests for preprocessing

Add tests proving that:

- 3-point averaging is applied before sublayer filtering;
- changing `Hmin` changes the filtered profile in the same way as the vendor
  workflow;
- classification of noisy raw data is stable after filtering.

### 4. Stress-model sensitivity tests

Because the public sources are incomplete about preliminary Stage-2 stress
assumptions, the code should include tests showing how much classification
changes when the stress model changes. If this sensitivity is material, expose
the assumption clearly in the UI/docs.

## Practical Notes for This Repo

If we upgrade the current implementation, the highest-value steps are:

1. replace nearest-centre classification with true area membership tests;
2. add `Undetermined` handling for outside-chart and missing-input cases;
3. implement the documented filtering workflow before classification;
4. use NEN subtype/material id as the raw segmentation key for the NEN route;
5. keep any app-side scalar score only as a QA/debug metric, not as the
   classification rule itself.

If this app intentionally keeps **raw unsmoothed input**, then item 3 becomes a
deliberate product deviation rather than a bug. In that case the highest-value
technical upgrades are:

1. digitise the actual chart areas;
2. classify by polygon/area membership instead of nearest-centre score;
3. add `Undetermined` handling;
4. use NEN subtype/material id as the raw segmentation key.

## Evidence Notes

- No public open-source implementation was identified and used as an
  authoritative reference during this audit.
- The public sources support the stress-correction concept, the 14-area chart,
  the preprocessing workflow, the material labels, the parameter mapping, and
  the `Undetermined` behaviour.
- The public sources do **not** expose a normative algebraic boundary formula
  equivalent to the full chart. That is why a faithful open implementation
  should digitise the actual chart areas and benchmark them against D-SHEET,
  rather than inventing a one-dimensional score as the primary rule.
