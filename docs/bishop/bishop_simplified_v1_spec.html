1Scope & Conventions

This document specifies the complete algorithmic pipeline from user-drawn terrain and CPT-derived soil layering through to a ranked list of Bishop Simplified factors of safety for circular slip surfaces. It is written so that a developer with no prior slope-stability experience can produce a working implementation. Every equation is given in computable form; every data flow is explicit.

The method implemented is Bishop Simplified (Bishop, 1955). It satisfies overall moment equilibrium about the circle centre and vertical force equilibrium per slice. It assumes zero interslice shear forces but retains interslice normal forces implicitly through the vertical equilibrium. This makes the factor of safety appear on both sides of the governing equation, requiring a simple fixed-point iteration that converges reliably for well-posed problems.

Accuracy context. Bishop Simplified typically agrees within 5% of rigorous methods (Spencer, Morgenstern–Price) for circular failure surfaces. It is the standard first-pass method in commercial tools (SLOPE/W, SLIDE, etc.) and is accepted by USACE EM 1110-2-1902, FHWA NHI-01-028, and Eurocode 7 annexes for circular analysis.
Current external-load support. The Stage 6 Bishop app supports one optional uniform vertical surcharge zone drawn on the terrain with the same two-click interaction as the entry and exit zones. It represents a strip surcharge over a finite horizontal interval, not a concentrated point load or an inclined load.

Unit system

All internal computation uses SI base units: metres (m), kilonewtons per cubic metre (kN/m³) for unit weights, kilopascals (kPa) for stresses and cohesion, degrees for friction angles (converted to radians for trigonometry). The solver is 2D plane-strain; all forces are per metre run of slope.

2Coordinate System & Sign Conventions

The coordinate system is right-handed with x pointing right (horizontal distance along slope cross-section) and y pointing up (elevation). The circle centre (xc, yc) always lies above the terrain. The slip circle arc runs from the entry point (higher elevation, typically the crest zone) to the exit point (lower elevation, typically the toe zone) in the positive x-direction.

The base angle α of each slice is defined as the angle between the slice-base chord and the horizontal, measured positive clockwise from horizontal. For a typical left-to-right descending slope, slices near the entry (active zone) have positive α, slices near the toe (passive zone) have negative α. This sign convention is critical and directly affects the moment arm calculation:

Base angle from circle geometry α_i = arctan( (y_base_left - y_base_right) / (x_right - x_left) ) Equivalently, from the circle centre: sin(α_i) = (x_mid_i - xc) / R where x_mid_i is the x-coordinate of the midpoint of slice i's base.
Critical implementation note. Use atan2 everywhere. Never use atan. The quadrant matters for slices that cross the lowest point of the circle where the sign of α flips. Using atan2(dy, dx) handles this automatically.

3Geometry Model

3.1Terrain polyline

The terrain surface is a piecewise-linear polyline defined by the user, stored as an ordered array of (x, y) vertices from left to right. The polyline must be monotonically increasing in x (no overhangs). The terrain defines the upper boundary of the soil mass.

Between any two consecutive terrain vertices, the surface elevation at arbitrary x is linearly interpolated:

Terrain interpolation y_terrain(x) = y_j + (y_{j+1} - y_j) × (x - x_j) / (x_{j+1} - x_j) where x_j ≤ x ≤ x_{j+1}

The implementation must provide a function terrainY(x) that performs this interpolation with binary search on the vertex array for efficiency. Outside the terrain extent, the function should extrapolate horizontally (constant y at the nearest endpoint), or reject the query depending on context.

3.2Soil regions from CPT layering

The CPT-derived layering from the existing app provides a vertical column of soil layers at each CPT location. Each layer has a top depth, bottom depth, and associated soil parameters (c', φ', γ). The slope stability module must convert these into 2D closed polygonal soil regions.

Layer interpolation between CPTs

Given two adjacent CPT locations at x-positions x_A and x_B, each with their own layer boundaries, the interpolation proceeds as follows:

  1. Match layers between CPTs by soil-type ID (not by depth). Each unique soil-type present in either CPT produces one region.
  2. Linear interpolation of layer boundaries: for each matched soil type, interpolate the top and bottom depth linearly between the two CPT positions. Where a layer exists in one CPT but not the adjacent one, either pinch it out (zero thickness at the far CPT) or flag the boundary as a lateral termination.
  3. Extend to terrain: the uppermost layer at each x must reach the terrain surface. If the CPT top-of-first-layer is below terrain, extend the first layer upward. If there is fill or topsoil above the CPT start depth, the user must define this as an explicit layer.
  4. Extend to depth: the deepest layer in each column extends downward to a defined model base (e.g. 5 m below the deepest slip circle considered) or to bedrock if defined.

Region polygon construction

Each soil region is stored as a closed polygon (array of vertices, counterclockwise winding). The regions must tile the model cross-section without gaps or overlaps. The polygon vertices come from the interpolated layer boundaries traced across the model width. Each region carries a single SoilType reference containing c', φ', γ, and optionally γ_sat for below-water calculations.

Why polygons, not depth arrays. Closed polygons make slice clipping (intersection of vertical strip with region polygon) a standard computational-geometry operation. They handle pinch-outs, lenses, and irregular boundaries cleanly. Every slice–layer intersection produces a sub-polygon whose area and centroid are computable with the shoelace formula. This is dramatically simpler and less error-prone than trying to track layer depths per-slice from raw arrays.

3.3Phreatic surface & pore-pressure model

The phreatic surface (groundwater table) is stored as another polyline, similar to the terrain. For v1, pore-water pressure at any point is computed from the vertical distance below the phreatic surface:

Hydrostatic pore pressure u(x, y) = γ_w × (y_phreatic(x) - y) if y < y_phreatic(x) u(x, y) = 0 if y ≥ y_phreatic(x) where γ_w = 9.81 kN/m³

The pore pressure relevant to each slice is evaluated at the midpoint of the slice base. For slices where the phreatic surface intersects the slice base, the average u across the base should be used (integrate linearly and divide by base length), but for v1 the midpoint value is acceptable and standard in most implementations.

Pore-pressure alternative: r_u method. If the app does not have a defined phreatic surface, an alternative is the pore-pressure ratio: u = r_u × γ × h where h is the height of the soil column above the slice base midpoint. This is a global simplification; r_u values of 0.0 (dry), 0.25 (typical), or 0.5 (high water table) are common. The phreatic-surface approach is preferred because it allows spatial variation.

3.4Uniform surcharge zone

The current load support beyond self-weight is one optional terrain-anchored surcharge zone. The zone is defined by its start and end x-coordinates on the terrain plus a uniform vertical intensity q. In engineering terms this is a strip surcharge over a finite width, evaluated per metre run of section.

Surface-load geometry surfaceLoad = { xStart: float, xEnd: float, q: float // kPa = kN/m² } Constraint: xStart < xEnd q ≥ 0

The load is applied only where a slice overlaps the interval [xStart, xEnd]. In the first version the direction is strictly vertical and downward. No horizontal component, no eccentricity, and no line-load singularity are introduced.

4Slip-Circle Definition & Search Strategy

4.1Circle parameterisation

A trial slip surface is a circular arc defined by three parameters: the centre coordinates (xc, yc) and the radius R. The arc intersects the terrain surface at exactly two points: the entry point (upslope) and the exit point (downslope). These intersection points define the horizontal extent of the sliding mass.

Given a circle and the terrain polyline, the entry and exit points are found by solving, for each terrain segment:

Circle–segment intersection Given terrain segment from (x1, y1) to (x2, y2): parametrise as P(t) = (x1, y1) + t × ((x2, y2) - (x1, y1)), t ∈ [0, 1] Substitute into circle equation: (P_x(t) - xc)² + (P_y(t) - yc)² = R² This yields a quadratic in t: a·t² + b·t + c = 0 where: dx = x2 - x1, dy = y2 - y1 fx = x1 - xc, fy = y1 - yc a = dx² + dy² b = 2·(fx·dx + fy·dy) c = fx² + fy² - R² Solutions t in [0, 1] give valid intersection points. Sort all valid intersections by x-coordinate → first = entry, last = exit.

A valid slip surface must have exactly two terrain intersections (entry and exit), and the entire arc between them must lie below the terrain. If the arc re-emerges through the terrain between entry and exit, the surface is multi-block and must be rejected in v1.

4.2Grid-radius search

The simplest search strategy discretises the space of possible circle centres and radii. Define a rectangular grid of candidate circle centres above the slope, and for each centre try a range of radii.

Grid bounds

  1. Horizontal extent: from x_crest − 0.5 × H to x_toe + 0.5 × H, where H is the slope height.
  2. Vertical extent: from y_crest to y_crest + 2 × H. Circle centres must be above the terrain.
  3. Grid spacing: start with H/10 in both directions. For a 10 m slope this gives 1 m spacing. After coarse search, refine around the best centre with spacing H/40.
  4. Radius range: for each centre, the minimum radius is the distance from the centre to the nearest terrain point (so the circle at least touches the terrain). The maximum radius is the distance from the centre to the deepest plausible failure depth. Try 10–20 radii per centre, linearly spaced.

Search size

A typical coarse search: 15 × 15 grid × 15 radii = 3,375 trial surfaces. Each Bishop iteration takes ~30 slices × ~5 iterations = ~150 evaluations, so the total is roughly 500,000 floating-point slice evaluations. This runs in well under 1 second on any modern device. The refinement pass adds another ~5,000 trials around the best centre. Total: well under 2 seconds.

4.3Entry-exit constraint mode

A more user-friendly alternative: instead of searching the (xc, yc, R) space, the user defines an entry zone (a segment of the terrain near the crest) and an exit zone (a segment near the toe). The search then generates circles that pass through all combinations of entry and exit points.

Given an entry point (x_en, y_en) and an exit point (x_ex, y_ex), the family of circles passing through both points is parameterised by one free parameter. The most natural choice is the circle centre's x-coordinate xc. Given two points on a circle:

Circle from two points + one parameter Given entry (x_en, y_en), exit (x_ex, y_ex), and chosen xc: From the circle equation applied to both points: (x_en - xc)² + (y_en - yc)² = R² (x_ex - xc)² + (y_ex - yc)² = R² Subtract to eliminate R²: yc = [ (x_en² - x_ex²) + (y_en² - y_ex²) - 2·xc·(x_en - x_ex) ] / [ 2·(y_en - y_ex) ] Then: R² = (x_en - xc)² + (y_en - yc)² Constraint: yc must be above terrain (circle centre above slope). Constraint: R must be large enough that the arc passes below the terrain between entry and exit.

Discretise the entry zone into ~10 points, the exit zone into ~10 points, and for each (entry, exit) pair sweep xc across ~15 values. This gives 10 × 10 × 15 = 1,500 trial surfaces — fast and well-constrained.

4.4Validity filters

Before running Bishop iteration on a trial circle, apply these filters (in order, cheapest first):

  1. Two-intersection test: the circle must intersect the terrain at exactly two points between entry and exit. Reject if zero, one, or more than two intersections.
  2. Minimum depth test: the maximum vertical distance from terrain to the arc (the depth of the slip at its deepest) must exceed a threshold, e.g. 0.5 m. Shallow surfaces are physically meaningless and numerically noisy.
  3. Entry/exit angle test: the angle at which the slip surface emerges through the terrain at the exit point must be less than a maximum, typically 60° from horizontal. Very steep exit angles produce unrealistic passive-zone geometry and convergence problems.
  4. No re-emergence test: verify the arc stays below the terrain between entry and exit. Sample 20+ points along the arc and check each is at or below the terrain. This catches circles that cut through intermediate benches or berms.
  5. Minimum slice count: after slicing (§5), require at least 5 valid slices. Fewer means the geometry is degenerate.
Performance note. Filter (1) and (2) eliminate the majority of invalid circles without ever building slices. Applying filters in cost order is essential for search performance. A rejected circle should cost only a circle-terrain intersection test, not a full slice build.

5Slice Generation

5.1Vertical-cut placement

Slices are vertical cuts through the sliding mass between the entry and exit x-coordinates. The cut positions are not uniform — they are placed at every geometric discontinuity, then intermediate cuts are added to limit maximum slice width.

Mandatory cut positions (sorted set of x-values)

  1. The entry x-coordinate (x_en).
  2. The exit x-coordinate (x_ex).
  3. Every terrain vertex x between x_en and x_ex (terrain slope breaks).
  4. Every soil-region boundary intersection with the vertical strip between x_en and x_ex. These are the x-positions where a layer boundary crosses the terrain surface or the slip-circle arc.
  5. The x-position where the phreatic surface crosses the slip-circle arc (if applicable).
  6. If a surcharge zone is present: its start and end x-coordinates, clipped to the entry-exit span.
  7. The x-position of the lowest point of the slip circle (where α changes sign), to prevent a single slice from spanning the sign change.

Intermediate cuts

After placing all mandatory cuts, inspect each resulting interval. If any interval is wider than (x_ex − x_en) / N_target where N_target = 30, subdivide it into equal sub-intervals until all slices are below the threshold width. This ensures roughly 30 slices minimum while honouring geometric boundaries.

Why 30 slices. GeoStudio documentation notes that beyond ~30 slices, the factor of safety changes negligibly. Fewer than ~10 can introduce meaningful discretisation error. 30 is a safe default; 50 is conservative; above 100 is wasted computation.

5.2Slice geometry extraction

For each slice between consecutive cuts at x_L and x_R, extract:

Slice geometry quantities Width: b = x_R - x_L Terrain elevation at edges: y_TL = terrainY(x_L) y_TR = terrainY(x_R) Circle elevation at edges (lower arc): y_CL = yc - sqrt(R² - (x_L - xc)²) y_CR = yc - sqrt(R² - (x_R - xc)²) Check: if (x - xc)² > R², this x is outside the circle → no valid slice. Always take the LOWER root (yc - sqrt) for the slip surface. Slice base midpoint: x_mid = (x_L + x_R) / 2 y_base_mid = yc - sqrt(R² - (x_mid - xc)²) y_top_mid = terrainY(x_mid) Base inclination angle: α = arcsin((x_mid - xc) / R) — or equivalently — α = atan2(y_CL - y_CR, x_R - x_L) Base length: l = b / cos(α)

5.3Multi-layer slices

A slice may pass through multiple soil layers between the terrain surface and the slip circle. The slice weight W must account for the contribution of each layer. The base properties (c', φ') come from the layer at the slip surface, not from layers above.

Weight calculation for multi-layer slice

For each slice, identify all soil regions that overlap with the vertical strip [x_L, x_R] × [y_circle, y_terrain]. For each overlapping region, compute the area of intersection (the sub-polygon formed by clipping the vertical strip against the region polygon), then:

Slice weight — multi-layer W_i = Σ_k ( A_k × γ_k ) where: A_k = area of region k within slice i (m²) γ_k = unit weight of region k (kN/m³) For the simplified case of horizontal or near-horizontal layering: A_k ≈ b × h_k where h_k is the average thickness of layer k within the slice. The base soil type is the region that contains the slice-base midpoint (x_mid, y_base_mid). c'_base = soilRegion(x_mid, y_base_mid).c_eff φ'_base = soilRegion(x_mid, y_base_mid).phi_eff
Simplification for v1. If layers are approximately horizontal (typical for CPT-derived profiles), the trapezoidal approximation A_k ≈ b × (h_k_left + h_k_right) / 2 is adequate and avoids polygon clipping. Full polygon clipping is needed only when layers are steeply inclined or pinch out within a slice.

Point-in-region test for base soil type

To determine which soil region contains the base midpoint, perform a standard point-in-polygon test (ray-casting or winding number) against each region polygon. Pre-sort regions so the deepest (lowest expected y) is tested first, since the base is always below the upper layers. Cache the region assignment per slice.

6Bishop Simplified Theory

6.1Free-body diagram & assumptions

Consider a single vertical slice through the sliding mass. The forces acting on it are:

  1. W — self-weight, acting vertically downward through the slice centroid.
  2. N' — effective normal force on the slice base, acting perpendicular to the base.
  3. u · l — pore-water force on the base, acting perpendicular to the base (opposite to N').
  4. S — shear force mobilised on the base, acting along the base (resisting sliding).
  5. E_L, E_R — interslice normal forces on the left and right vertical faces.
  6. X_L, X_R — interslice shear forces on the left and right vertical faces.

Bishop Simplified assumptions:

  1. The interslice shear forces are zero: X_L = X_R = 0 for all slices. This is the defining simplification. It does not mean interslice normal forces are zero — they are implicitly determined by vertical equilibrium.
  2. The Mohr–Coulomb failure criterion applies on the base: τ_f = c' + (σ_n - u) × tan(φ').
  3. The mobilised shear stress is τ_m = τ_f / F, where F is the factor of safety (uniform along the entire slip surface).
  4. Moment equilibrium is taken about the circle centre, which causes the normal force and pore pressure (both radial) to vanish from the moment equation.

6.2Governing equation derivation

Starting from vertical force equilibrium on a single slice (with X_L = X_R = 0):

Vertical equilibrium per slice W = N'·cos(α) + u·l·cos(α) + S·sin(α) where S = (1/F) × (c'·l + N'·tan(φ')) Substitute S and solve for N': W = N'·cos(α) + u·l·cos(α) + (sin(α)/F)·(c'·l + N'·tan(φ')) N'·[cos(α) + sin(α)·tan(φ')/F] = W - u·l·cos(α) - c'·l·sin(α)/F Define: m_α = cos(α) + sin(α)·tan(φ')/F Then: N' = [W - u·l·cos(α) - c'·l·sin(α)/F] / m_α

Now take moment equilibrium about the circle centre. The moment arm for W is R·sin(α) (driving). The moment arm for S is R (resisting — because shear on the base is tangential to the circle, so its lever arm to the centre is always R). The normal force N' and the pore-pressure force u·l are both radial, so their moment about the centre is zero.

Moment equilibrium about circle centre Σ W_i · R · sin(α_i) = Σ S_i · R The R cancels: Σ W_i · sin(α_i) = Σ S_i Since S_i = (1/F) × (c'_i · l_i + N'_i · tan(φ'_i)): F = Σ (c'_i · l_i + N'_i · tan(φ'_i)) / Σ W_i · sin(α_i)

Now substitute the expression for N' and use l = b / cos(α):

Bishop Simplified — final governing equation Σ [ (c'·b + (W - u·b)·tan(φ')) × (1 / m_α) ] F = ───────────────────────────────────────────────────── Σ [ W · sin(α) ] where: m_α(i) = cos(α_i) + sin(α_i) · tan(φ'_i) / F For each slice i: numerator term: [ c'_i · b_i + (W_i - u_i · b_i) · tan(φ'_i) ] / m_α(i) denominator term: W_i · sin(α_i)
Critical subtlety. In the numerator, the pore-pressure term is u · b, not u · l. This is because when you substitute l = b / cos(α) and multiply through by cos(α) to form m_α, the l · cos(α) simplifies to b. Getting this wrong (using u·l instead of u·b) is the single most common implementation error in Bishop Simplified and will produce wrong factors of safety. Verify this in your derivation.

6.3Iteration scheme

Because F appears on both sides of the equation (inside m_α on the right-hand side and as the overall ratio), the equation must be solved iteratively. The standard approach is simple fixed-point iteration (successive substitution):

Fixed-point iteration 1. Choose initial guess: F⁰ = F_Fellenius (or simply F⁰ = 1.0) 2. For iteration k = 0, 1, 2, ...: a. For each slice i, compute: m_α(i) = cos(α_i) + sin(α_i) · tan(φ'_i) / F^k b. Compute: numerator = Σ_i [ (c'_i · b_i + (W_i - u_i · b_i) · tan(φ'_i)) / m_α(i) ] denominator = Σ_i [ W_i · sin(α_i) ] c. New estimate: F^{k+1} = numerator / denominator 3. Stop when |F^{k+1} - F^k| < tolerance (tolerance = 1e-4)

Initial guess: Ordinary (Fellenius) method

A good initial guess accelerates convergence. The Ordinary Method of Slices (Fellenius, 1927) does not require iteration and provides a useful starting point:

Fellenius factor of safety (initial guess) Σ [ c'_i · l_i + (W_i · cos(α_i) - u_i · l_i) · tan(φ'_i) ] F_Fellenius = ───────────────────────────────────────────────────────────────── Σ [ W_i · sin(α_i) ] This satisfies only moment equilibrium without vertical force equilibrium per slice. It typically underestimates F by 5–15% compared to Bishop.

6.4Convergence criteria & failure modes

Bishop Simplified converges rapidly — typically 4–6 iterations for well-posed problems. However, certain conditions cause trouble:

ConditionSymptomAction
m_α ≤ 0 for any slice Division by zero or negative denominator → F oscillates or diverges Reject this trial surface. This occurs when α is steeply negative (passive zone) and tan(φ')/F is large. It is a known limitation of Bishop Simplified for deep-seated failures with steep exit angles.
Denominator Σ W·sin(α) ≤ 0 F becomes negative or infinite Reject. This means the slip surface has no net driving moment — it is not a physically meaningful failure.
No convergence in 50 iterations F oscillates between two values or drifts Reject and flag. Consider under-relaxation: F^{k+1} = ω·F_new + (1-ω)·F^k with ω = 0.5. If this still fails after 50 iterations, the surface is genuinely problematic.
F < 0.1 during iteration Extreme instability — possibly a numerical artifact Flag as potentially unstable but do not reject outright. Very low F values can be real for steep, weak slopes.
Under-relaxation implementation. If during any iteration k the change |F^{k+1} − F^k| increases compared to the previous step (i.e. the iteration is diverging), switch to under-relaxed updates: F^{k+1} = 0.5 × F_new + 0.5 × F^k. This damps oscillation without affecting the final converged value.

6.5Uniform surcharge contribution

The current load implementation adds one vertical surcharge term to each slice. The surcharge is treated as an added vertical load contribution Q_i over the part of the slice width that overlaps the drawn terrain interval.

Slice surcharge overlap b_load,i = max(0, min(x_R,i, x_q,end) - max(x_L,i, x_q,start)) Q_i = q × b_load,i V_i = W_i + Q_i

The surcharge is vertical and downward only, so the Bishop algebra stays almost unchanged: replace the slice vertical load W_i by V_i wherever the solver currently uses the total downward slice force.

Bishop equation with surcharge zone Σ [ (c'·b + (V - u·b)·tan(φ')) × (1 / m_α) ] F = ───────────────────────────────────────────────────── Σ [ V · sin(α) ] where: V_i = W_i + Q_i
Vertical equilibrium with surcharge V = N'·cos(α) + u·b + S·sin(α) with: V = W + Q
Implementation consequence. The load-zone start and end x-values must be part of the mandatory cut set (§5.1), and the slice data structure should retain both Q_i and V_i for result inspection. This keeps the visual diagnostics honest: users can see soil weight, surcharge, and total vertical load separately.

7Data Structures

The following data structures define the complete state required by the solver. They are language-agnostic; adapt to your stack's conventions (classes, structs, interfaces, typed objects).

  y: float    // elevation (m)
}

struct Polyline {

}

  id:          string     // unique identifier
  c_eff:       float      // effective cohesion c' (kPa)
  phi_eff:     float      // effective friction angle φ' (degrees)
  gamma:       float      // total unit weight γ (kN/m³)
  gamma_sat:   float      // saturated unit weight (kN/m³), optional
}

struct SoilRegion {
  polygon:    Point[]    // closed polygon, CCW winding
  soilType:   SoilType   // material reference

  containsPoint(p: Point): bool
    // ray-casting point-in-polygon test

  clipToVerticalStrip(xL, xR): Point[]
    // Sutherland–Hodgman clip against x=xL, x=xR

  area(): float
    // shoelace formula on polygon
}

// ── Slip circle ──

struct SlipCircle {
  xc: float      // centre x (m)
  yc: float      // centre y (m)
  R:  float      // radius (m)

  yCircle(x): float
    // yc - sqrt(R² - (x - xc)²)  — lower arc
    // returns NaN if |x - xc| > R

  baseAngle(x): float
    // asin((x - xc) / R)  in radians
}

// ── Slice ──

struct Slice {
  index:       int
  xL:          float       // left edge x
  xR:          float       // right edge x
  b:           float       // width = xR - xL
  xMid:        float       // midpoint x
  yTop:        float       // terrain at xMid
  yBase:       float       // circle at xMid

8.1Geometry & region builder

// ────────────────────────────────────────────────────────────
// terrainY: interpolate terrain elevation at arbitrary x
// ────────────────────────────────────────────────────────────
function terrainY(terrain: Polyline, x: float) → float:
  let verts = terrain.vertices
  if x ≤ verts[0].x: return verts[0].y
  if x ≥ verts[last].x: return verts[last].y

  // binary search for segment [j, j+1] containing x
  let j = binarySearchSegment(verts, x)
  let t = (x - verts[j].x) / (verts[j+1].x - verts[j].x)
  return verts[j].y + t × (verts[j+1].y - verts[j].y)


// ────────────────────────────────────────────────────────────
// buildSoilRegions: convert CPT layer columns to 2D polygons
// ────────────────────────────────────────────────────────────
function buildSoilRegions(
  cptLocations: {x: float, layers: {topDepth, botDepth, soilTypeId}[]}[],
  terrain: Polyline,
  modelBase: float    // y-coordinate of model bottom
) → SoilRegion[]:

  // Step 1: collect all unique soil type IDs across all CPTs
  let allTypeIds = unique set of soilTypeId from all CPT layers

  let regions = []

  for each typeId in allTypeIds:
    let topProfile = []   // (x, y) pairs tracing top of this layer
    let botProfile = []   // (x, y) pairs tracing bottom of this layer

    for each cpt in cptLocations (sorted by x):
      let layer = cpt.layers.find(soilTypeId == typeId)
      let yTerrain = terrainY(terrain, cpt.x)

      if layer exists:
        // CPT depths are below terrain surface → convert to elevation
        let yTop = yTerrain - layer.topDepth
        let yBot = yTerrain - layer.botDepth
        // Clamp top to terrain if it's the shallowest layer
        if yTop > yTerrain: yTop = yTerrain
        // Clamp bottom to model base
        if yBot < modelBase: yBot = modelBase
        topProfile.push({x: cpt.x, y: yTop})
        botProfile.push({x: cpt.x, y: yBot})
      else:
        // Layer absent at this CPT → pinch out (zero thickness)
        let yPinch = interpolate from adjacent CPTs or terrain
        topProfile.push({x: cpt.x, y: yPinch})
        botProfile.push({x: cpt.x, y: yPinch})

    // Step 2: form closed polygon
    // trace top left→right, then bottom right→left
    let polygon = topProfile + reverse(botProfile)
    // close the polygon
    polygon.push(polygon[0])

    regions.push(SoilRegion {
      polygon: polygon,
      soilType: lookupSoilType(typeId)
    })

  return regions


// ────────────────────────────────────────────────────────────
// shoelaceArea: signed area of a closed polygon
// Positive = CCW, Negative = CW
// ────────────────────────────────────────────────────────────
function shoelaceArea(poly: Point[]) → float:
  let n = poly.length
  let area = 0.0
  for i = 0 to n-2:
    area += poly[i].x × poly[i+1].y - poly[i+1].x × poly[i].y
  return area / 2.0

8.2Circle-terrain intersection

// ────────────────────────────────────────────────────────────
// findCircleTerrainIntersections
// Returns intersection points sorted by x, from entry to exit
// ────────────────────────────────────────────────────────────
function findCircleTerrainIntersections(
  circle: SlipCircle,
  terrain: Polyline
) → Point[]:
  let intersections = []

  for each segment (p1, p2) in terrain.vertices (consecutive pairs):
    let dx = p2.x - p1.x
    let dy = p2.y - p1.y
    let fx = p1.x - circle.xc
    let fy = p1.y - circle.yc

    let a = dx×dx + dy×dy
    let b_coeff = 2.0 × (fx×dx + fy×dy)
    let c = fx×fx + fy×fy - circle.R × circle.R

    let discriminant = b_coeff×b_coeff - 4.0×a×c

    if discriminant < 0: continue  // no intersection with this segment

    let sqrtDisc = sqrt(discriminant)

    for sign in [-1, +1]:
      let t = (-b_coeff + sign × sqrtDisc) / (2.0 × a)

      // t must be in [0, 1] to lie on this segment
      // use small epsilon for boundary tolerance
      if t < -1e-9 or t > 1.0 + 1e-9: continue
      t = clamp(t, 0.0, 1.0)

      let px = p1.x + t × dx
      let py = p1.y + t × dy

      // deduplicate: skip if too close to an existing intersection
      if not any(intersections, p → dist(p, {px, py}) < 1e-6):
        intersections.push({x: px, y: py})

  // sort by x ascending
  intersections.sortBy(p → p.x)
  return intersections


// ────────────────────────────────────────────────────────────
// validateSlipCircle: apply all validity filters
// ────────────────────────────────────────────────────────────
function validateSlipCircle(
  circle: SlipCircle,
  terrain: Polyline,
  config: {
    minDepth: float,          // default 0.5 m
    maxExitAngle: float,       // default 60° (in radians)
    nCheckPoints: int          // default 30
  }
) → {valid: bool, entry: Point, exit: Point, reason: string}:

  let ints = findCircleTerrainIntersections(circle, terrain)

  // Filter 1: exactly 2 intersections
  if ints.length ≠ 2:
    return {valid: false, reason: "need exactly 2 terrain intersections, got " + ints.length}

  let entry = ints[0]   // leftmost (upslope)
  let exit  = ints[1]   // rightmost (downslope)

  // Filter 2: minimum depth
  let xMid = (entry.x + exit.x) / 2.0
  let depth = terrainY(terrain, xMid) - circle.yCircle(xMid)
  if depth < config.minDepth:
    return {valid: false, reason: "max depth " + depth + " < min " + config.minDepth}

  // Filter 3: exit angle
  let exitAngle = abs(circle.baseAngle(exit.x))
  if exitAngle > config.maxExitAngle:
    return {valid: false, reason: "exit angle " + degrees(exitAngle) + "° > max"}

  // Filter 4: no re-emergence
  let dx = (exit.x - entry.x) / config.nCheckPoints
  for k = 1 to config.nCheckPoints - 1:
    let xCheck = entry.x + k × dx
    let yCircleCheck = circle.yCircle(xCheck)
    let yTerrainCheck = terrainY(terrain, xCheck)
    if yCircleCheck > yTerrainCheck + 1e-4:
      return {valid: false, reason: "circle re-emerges above terrain at x=" + xCheck}

  return {valid: true, entry: entry, exit: exit, reason: ""}

8.3Slice builder

// ────────────────────────────────────────────────────────────
// buildSlices: generate vertical slices between entry and exit
// ────────────────────────────────────────────────────────────
function buildSlices(
  circle: SlipCircle,
  entry: Point,
  exit: Point,
  model: SlopeModel,
  nTarget: int = 30
) → Slice[]:

  // ── Step 1: collect mandatory cut x-positions ──
  let cuts = SortedSet()
  cuts.add(entry.x)
  cuts.add(exit.x)

  // terrain vertices within [entry.x, exit.x]
  for each v in model.terrain.vertices:
    if v.x > entry.x + 1e-6 and v.x < exit.x - 1e-6:
      cuts.add(v.x)

  // phreatic surface vertices
  if model.phreatic ≠ null:
    for each v in model.phreatic.vertices:
      if v.x > entry.x + 1e-6 and v.x < exit.x - 1e-6:
        cuts.add(v.x)

  // x where α = 0 (lowest point of circle)
  if circle.xc > entry.x and circle.xc < exit.x:
    cuts.add(circle.xc)

  // soil-region boundary intersections with the arc
  // For each region polygon edge, find where it intersects
  // the slip circle arc between entry.x and exit.x
  for each region in model.regions:
    for each edge (p1, p2) in region.polygon:
      let ixs = circleSegmentIntersections(circle, p1, p2)
      for each ix in ixs:
        if ix.x > entry.x + 1e-6 and ix.x < exit.x - 1e-6:
          cuts.add(ix.x)

  // ── Step 2: subdivide wide intervals ──
  let maxWidth = (exit.x - entry.x) / nTarget
  let finalCuts = SortedSet()
  let cutList = cuts.toArray()

  for i = 0 to cutList.length - 2:
    finalCuts.add(cutList[i])
    let gap = cutList[i+1] - cutList[i]
    if gap > maxWidth:
      let nSub = ceil(gap / maxWidth)
      let subWidth = gap / nSub
      for j = 1 to nSub - 1:
        finalCuts.add(cutList[i] + j × subWidth)
  finalCuts.add(cutList[last])

  // ── Step 3: build slice objects ──
  let cutArr = finalCuts.toArray()
  let slices = []

  for i = 0 to cutArr.length - 2:
    let xL = cutArr[i]
    let xR = cutArr[i + 1]
    let b  = xR - xL
    if b < 1e-6: continue  // degenerate slice

    let xMid = (xL + xR) / 2.0

    // terrain and circle at midpoint
    let yTop  = terrainY(model.terrain, xMid)
    let yBase = circle.yCircle(xMid)

    if yBase ≥ yTop: continue  // circle above terrain → invalid slice

    // base angle
    let alpha = asin(clamp((xMid - circle.xc) / circle.R, -1.0, 1.0))

    // base length
    let cosAlpha = cos(alpha)
    if abs(cosAlpha) < 1e-10: continue  // near-vertical base → degenerate
    let baseLength = b / cosAlpha

    // ── weight: sum contributions from each soil region ──
    let W = 0.0
    let layerAreas = []

    for each region in model.regions:
      // clip region polygon to vertical strip [xL, xR]
      let clipped = clipPolygonToStrip(region.polygon, xL, xR)
      if clipped is empty: continue

      // further clip to [yBase, yTop] vertical extent
      // (clip below terrain and above circle)
      let sliceClipped = clipPolygonToHorizontalBand(clipped, yBase, yTop)
      // Note: for full accuracy, the lower boundary is the arc, not
      // a horizontal line. For v1 with ~30 narrow slices, using
      // yBase at midpoint as the lower clip is adequate.

      let A = abs(shoelaceArea(sliceClipped))
      if A > 1e-8:
        W += A × region.soilType.gamma
        layerAreas.push({soilType: region.soilType, area: A})

    // ── simplified weight for near-horizontal layers ──
    // Alternative if polygon clipping is not yet implemented:
    // W = b × (yTop - yBase) × γ_weighted_average
    // where γ_weighted_average weights each layer's γ by its
    // thickness fraction within the slice column.

    // ── pore pressure ──
    let u = 0.0
    if model.phreatic ≠ null:
      let yPhreatic = model.phreatic.interpolateY(xMid)
      if yBase < yPhreatic:
        u = 9.81 × (yPhreatic - yBase)

    // ── base soil properties ──
    let baseSoil = findRegionContaining(model.regions, {x: xMid, y: yBase + 0.01})
    // offset slightly above base to ensure point is inside the soil mass
    // not below the circle

    slices.push(Slice {
      index: slices.length,
      xL: xL, xR: xR, b: b, xMid: xMid,
      yTop: yTop, yBase: yBase,
      alpha: alpha,
      baseLength: baseLength,
      W: W, u: u,
      c_eff: baseSoil.soilType.c_eff,
      phi_eff: toRadians(baseSoil.soilType.phi_eff),
      layerAreas: layerAreas
    })

  return slices


// ────────────────────────────────────────────────────────────
// findRegionContaining: point-in-polygon test across all regions
// ────────────────────────────────────────────────────────────
function findRegionContaining(
  regions: SoilRegion[],
  point: Point
) → SoilRegion:
  for each region in regions:
    if region.containsPoint(point):
      return region
  // fallback: return the deepest region (last in array)
  // This should not happen if regions tile the model correctly
  throw "No soil region contains point (" + point.x + ", " + point.y + ")"

8.4Bishop iteration loop

// ────────────────────────────────────────────────────────────
// computeBishopF: iterate to find factor of safety
// This is the core solver.
// ────────────────────────────────────────────────────────────
function computeBishopF(
  slices: Slice[],
  maxIter: int = 50,
  tolerance: float = 0.001
) → {F: float, converged: bool, iterations: int, F_fellenius: float}:

  // ── Step 0: pre-check denominator ──
  let sumWsinAlpha = 0.0
  for each s in slices:
    sumWsinAlpha += s.W × sin(s.alpha)

  if sumWsinAlpha ≤ 0.001:
    // no net driving moment → not a meaningful failure
    return {F: Infinity, converged: false, iterations: 0,
            F_fellenius: Infinity}

  // ── Step 1: compute Fellenius F as initial guess ──
  let felleniusNum = 0.0
  for each s in slices:
    let l = s.baseLength
    let normalComponent = s.W × cos(s.alpha) - s.u × l
    felleniusNum += s.c_eff × l + normalComponent × tan(s.phi_eff)

  let F_fellenius = felleniusNum / sumWsinAlpha
  if F_fellenius < 0.1: F_fellenius = 1.0  // safety floor for initial guess

  // ── Step 2: Bishop iteration ──
  let F = F_fellenius
  let prevChange = Infinity
  let useRelaxation = false

  for iter = 1 to maxIter:
    let numerator = 0.0
    let mAlphaOk = true

    for each s in slices:
      // m_α = cos(α) + sin(α)·tan(φ') / F
      let mAlpha = cos(s.alpha) + sin(s.alpha) × tan(s.phi_eff) / F

      if mAlpha ≤ 0.0:
        mAlphaOk = false
        break

      // Bishop numerator term for this slice:
      // [c'·b + (W - u·b)·tan(φ')] / m_α
      //
      // CRITICAL: the pore-pressure term uses u·b, NOT u·l
      // This is a consequence of the derivation — see §6.2
      let term = (s.c_eff × s.b + (s.W - s.u × s.b) × tan(s.phi_eff)) / mAlpha

      numerator += term

    if not mAlphaOk:
      return {F: F, converged: false, iterations: iter,
              F_fellenius: F_fellenius}

    let F_new = numerator / sumWsinAlpha
    let change = abs(F_new - F)

    // divergence detection → switch to under-relaxation
    if change > prevChange and not useRelaxation:
      useRelaxation = true

    if useRelaxation:
      F = 0.5 × F_new + 0.5 × F
    else:
      F = F_new

    // convergence check
    if change < tolerance:
      return {F: F, converged: true, iterations: iter,
              F_fellenius: F_fellenius}

    prevChange = change

  // failed to converge
  return {F: F, converged: false, iterations: maxIter,
          F_fellenius: F_fellenius}

// ────────────────────────────────────────────────────────────
// searchGridRadius: coarse grid search + refinement
// ────────────────────────────────────────────────────────────
function searchGridRadius(
  model: SlopeModel,
  config: {
    gridNx: int,        // default 15
    gridNy: int,        // default 15
    nRadii: int,        // default 15
    refineNx: int,      // default 7
    refineNy: int,      // default 7
    refineNr: int,      // default 7
    nSlices: int,       // default 30
    keepBest: int       // default 10
  }
) → SearchResult:

  // ── determine slope extents ──
  let xMin = model.terrain.vertices[0].x
  let xMax = model.terrain.vertices[last].x
  let yMin = min(v.y for v in model.terrain.vertices)
  let yMax = max(v.y for v in model.terrain.vertices)
  let H    = yMax - yMin   // slope height

  // ── coarse grid bounds ──
  let xc_min = xMin - 0.5 × H
  let xc_max = xMax + 0.5 × H
  let yc_min = yMax              // at crest elevation
  let yc_max = yMax + 2.0 × H    // well above slope

  let dx = (xc_max - xc_min) / config.gridNx
  let dy = (yc_max - yc_min) / config.gridNy

  let allResults = []
  let trialsTotal = 0
  let trialsRejected = 0

  // ── Phase 1: coarse search ──
  for ix = 0 to config.gridNx:
    for iy = 0 to config.gridNy:
      let xc = xc_min + ix × dx
      let yc = yc_min + iy × dy

      // radius range: minimum = distance to nearest terrain point
      let R_min = minDistToTerrain(xc, yc, model.terrain) + 0.1
      let R_max = sqrt((xc - xMin)² + (yc - yMin)²) + H
      if R_max ≤ R_min: continue

      let dR = (R_max - R_min) / config.nRadii

      for ir = 0 to config.nRadii:
        let R = R_min + ir × dR
        let circle = SlipCircle {xc, yc, R}

        trialsTotal += 1

        // validate
        let v = validateSlipCircle(circle, model.terrain,
                {minDepth: 0.5, maxExitAngle: toRadians(60), nCheckPoints: 30})
        if not v.valid:
          trialsRejected += 1
          continue

        // build slices
        let slices = buildSlices(circle, v.entry, v.exit, model, config.nSlices)
        if slices.length < 5:
          trialsRejected += 1
          continue

        // solve Bishop
        let result = computeBishopF(slices)

        allResults.push(BishopResult {
          circle: circle,
          F: result.F,
          converged: result.converged,
          iterations: result.iterations,
          slices: slices,
          F_fellenius: result.F_fellenius,
          rejected: not result.converged,
          rejectReason: result.converged ? "" : "no convergence"
        })

  // ── Phase 2: refinement around best centre ──
  let validResults = allResults.filter(r → r.converged and r.F > 0)
  validResults.sortBy(r → r.F)

  if validResults.length > 0:
    let best = validResults[0]
    let refDx = dx / config.refineNx
    let refDy = dy / config.refineNy

    for ix = -config.refineNx to config.refineNx:
      for iy = -config.refineNy to config.refineNy:
        let xc = best.circle.xc + ix × refDx
        let yc = best.circle.yc + iy × refDy

        let R_center = best.circle.R
        let dR_ref = (dx + dy) / 2.0 / config.refineNr

        for ir = -config.refineNr to config.refineNr:
          let R = R_center + ir × dR_ref
          if R ≤ 0: continue

          let circle = SlipCircle {xc, yc, R}
          trialsTotal += 1

          // ... same validate → buildSlices → computeBishopF pipeline ...
          // (identical to coarse phase above)

  // ── collect and rank ──
  let finalValid = allResults.filter(r → r.converged and r.F > 0)
  finalValid.sortBy(r → r.F)

  return SearchResult {
    results: finalValid.take(config.keepBest),
    critical: finalValid[0],
    trialsTotal: trialsTotal,
    trialsValid: finalValid.length,
    trialsRejected: trialsRejected
  }

9Pore-Pressure Handling

Three pore-pressure models are supported, in order of sophistication:

Model A: Dry (u = 0)

No phreatic surface defined. All slices have u = 0. Suitable for quick checks or naturally drained slopes above the water table.

Model B: Pore-pressure ratio r_u

A single global ratio applied to all slices:

u_i = r_u × γ_i × h_i where h_i = yTop_i - yBase_i (height of soil column above base midpoint) and γ_i is the average unit weight of the slice column.

Typical values: r_u = 0 (dry), 0.25 (moderate), 0.5 (high water table). This is a crude but useful approximation when no phreatic data is available.

Model C: Phreatic surface (recommended)

As described in §3.3. The phreatic polyline is interpolated at each slice base midpoint. This is the default and recommended approach because it allows spatial variation of pore pressure reflecting real groundwater conditions.

Submerged unit weight. In v1, use total unit weight γ for W and subtract u·b in the Bishop formula. Do not try to separate the calculation into γ' (submerged) above and below the water table — the Bishop formula already handles this correctly through the (W - u·b) term, where W uses total weight. Using γ' would double-count the buoyancy effect.

Below-water weight handling

When the phreatic surface is above the slice base but below the terrain, the slice column has a submerged portion. The weight calculation uses total unit weight throughout:

Weight with partial submersion W = Σ (A_k × γ_k) Use γ_sat for layers below the phreatic surface, and γ (natural/dry) for layers above. The pore pressure u at the base handles the effective-stress correction in the Bishop equation. Do NOT subtract buoyancy from W — the formula does this via the (W - u·b) term.

11Upgrade Path to Spencer / Morgenstern–Price

The architecture of the solver is designed to make the upgrade to rigorous methods incremental. The key additions for each method are outlined below.

Spencer (constant interslice-force ratio)

Spencer (1967) satisfies both moment and force equilibrium simultaneously. It assumes that the ratio of interslice shear to interslice normal force is constant: X/E = λ = constant (the same for all slices).

Implementation requires:

  1. A second equation: overall horizontal force equilibrium (in addition to moment equilibrium).
  2. An outer loop that iterates on λ until both equilibrium equations yield the same F.
  3. An inner loop (per trial λ) that iterates on F via the same Bishop-like scheme but with modified m_α that includes the interslice force contribution.
  4. The slice data structure already contains everything needed. The only addition is tracking E and X arrays (interslice forces, n-1 values for n slices).

The practical approach: for each shortlisted Bishop surface (top 5–10), re-run with Spencer. If Bishop and Spencer agree within 5%, Bishop is sufficient. If they diverge, the Spencer result is more reliable.

Morgenstern–Price (general interslice-force function)

Generalises Spencer by allowing the interslice force ratio to vary along the slip surface: X/E = λ · f(x) where f(x) is a prescribed function (half-sine, constant, trapezoidal, etc.).

This adds complexity mainly in the iteration scheme (two unknowns: F and λ, solved by Newton–Raphson or bisection on the two equilibrium equations). The slice-level calculations are the same. For most practical problems with circular slip surfaces, Spencer and M-P give nearly identical results. M-P is primarily valuable for non-circular surfaces where the interslice force distribution matters more.

Recommended v2 strategy. After Bishop v1 is verified and stable, add Spencer as the first rigorous check method. Use it to validate Bishop results on your critical surfaces. Only add M-P if you encounter non-circular failure scenarios (thin weak seams, defined interfaces) that Bishop cannot model. Even then, the geometry engine (non-circular surface definition, composite surface search) is a bigger development effort than the M-P solver itself.

12Interactive Canvas — Drawing & Editing

The entire geometry model — terrain, CPT positions, phreatic surface, entry/exit zones, and soil regions — is constructed by the user on a 2D canvas. The canvas is the single source of truth for all geometry that feeds the solver. Nothing is typed into tables or imported from files in v1; every geometric input is drawn or placed graphically and can be edited graphically. The solver only runs on what the canvas contains.

12.1Canvas coordinate system & viewport

The canvas operates in two coordinate spaces that must be kept rigorously separate throughout the codebase:

SpaceUnitsOriginY directionUsed for
World spacemetresarbitrary (user-defined datum)up = positiveAll engineering data: terrain vertices, circle centres, slice geometry, solver input. Persisted in the model.
Screen spaceCSS pixelstop-left of canvas elementdown = positiveAll rendering, hit-testing, mouse/touch coordinates. Ephemeral — recomputed on every frame.

Viewport transform

The mapping between world and screen is an affine transform defined by three parameters: pan offset (panX, panY) in pixels and a zoom scale factor scale (pixels per metre). The transform is:

World → Screen screenX = (worldX - panX) × scale screenY = canvasHeight - (worldY - panY) × scale The Y-flip (canvasHeight − …) is essential because screen Y increases downward while world Y increases upward.
Screen → World (inverse, for mouse events) worldX = screenX / scale + panX worldY = (canvasHeight - screenY) / scale + panY

Viewport behaviour

  1. Pan: middle-mouse drag or two-finger drag updates panX, panY. Pan is in world units.
  2. Zoom: scroll wheel or pinch adjusts scale. Zoom towards the cursor position (the world point under the cursor must remain stationary after zoom). Implementation: compute world point under cursor before zoom, adjust scale, recompute panX/panY so the same world point maps back to the same screen pixel.
  3. Fit-to-extents: a button or keyboard shortcut (F key) auto-fits the viewport so the terrain polyline plus a 10% margin fills the canvas. Compute bounding box of terrain vertices, then set scale and pan so the box fits with padding.
  4. Aspect ratio: always 1:1 (no distortion). The same scale value applies to both axes. This is non-negotiable — a distorted cross-section produces wrong visual intuition about slope angles.
Exaggeration option (v2). Some users may want vertical exaggeration (e.g. 2× or 5×) for very flat slopes. Do not implement this in v1. It complicates the screen↔world transform, breaks circle rendering (circles become ellipses), and creates misleading visual impressions. If added later, it must be clearly labelled and disabled during solver visualization.

Grid & axis display

Draw a background grid in world-space coordinates. Grid spacing adapts to zoom level: at zoom where 1 m = 20+ px, show 1 m major grid + 0.5 m minor grid; at zoom where 1 m = 5–20 px, show 5 m major + 1 m minor; at zoom where 1 m < 5 px, show 10 m major + 5 m minor. Axis labels (elevation in m above datum, horizontal distance in m) appear along the left and bottom edges. The grid is drawn first (lowest z-order) so all geometry draws on top of it.

12.2Terrain drawing tool

The terrain polyline is the first thing the user draws. It defines the upper boundary of the entire model.

Drawing mode

  1. User activates the terrain tool (toolbar button or T key).
  2. Each click/tap places a vertex at the world coordinates under the cursor. The vertex snaps to the grid if grid-snap is enabled (default: on, snap to 0.5 m).
  3. A rubber-band line follows the cursor from the last placed vertex to the current cursor position, showing the next segment before placement.
  4. The terrain is drawn left-to-right. If the user clicks at an x-coordinate less than or equal to the previous vertex, reject the click and flash a visual warning. The terrain must be monotonically increasing in x.
  5. Double-click or press Enter / Escape to finish the polyline.
  6. Minimum 3 vertices required. If the user finishes with fewer, discard and stay in drawing mode.

Visual feedback during drawing

  • Placed vertices: solid circles (6 px radius), accent colour.
  • Placed segments: solid lines (2 px), accent colour.
  • Rubber-band segment: dashed line (1.5 px), lighter accent colour.
  • Cursor coordinate readout: small tooltip near cursor showing (x, y) in metres, updated in real time.
  • Cumulative terrain length displayed in the status bar.

Post-drawing editing

After the terrain is placed, it becomes editable (§12.6). Vertices can be dragged, inserted, or deleted. The monotonicity constraint must be enforced during drag: a vertex cannot be dragged past its neighbours in x.

12.3CPT placement & layer adoption

CPTs are the source of soil layering. The user places CPT markers on the terrain, and the app imports layering from the existing CPT interpretation pipeline.

Placement

  1. User activates the CPT tool (toolbar button or C key).
  2. Click on or near the terrain polyline to place a CPT. The CPT marker snaps to the terrain surface: the x-coordinate is taken from the click, the y-coordinate is set to terrainY(x). Visual: a vertical pin/marker icon extending downward from the terrain.
  3. On placement, the app must resolve which CPT data to associate. Two modes:
    • Auto-link: if the existing app has CPT data indexed by location, match the placed position to the nearest available CPT dataset (within a configurable tolerance, e.g. 5 m). Show the matched CPT ID in a tooltip.
    • Manual selection: a dropdown/modal appears listing available CPTs from the project; the user picks one.
  4. Once linked, the CPT's interpreted layer column is immediately available. The app draws the layer boundaries extending downward from the terrain surface at the CPT's x-position.

Layer adoption & interpolation visualisation

When two or more CPTs are placed, the app interpolates layer boundaries between them (as specified in §3.2) and fills the cross-section with soil regions. This interpolation must happen live as each CPT is placed — the user should see the layering update immediately. Specifically:

  1. Single CPT: layers extend horizontally across the full model width (constant depth from terrain). This is a placeholder until a second CPT constrains the interpolation.
  2. Two+ CPTs: layers are linearly interpolated between adjacent CPTs. Beyond the leftmost and rightmost CPTs, layers are extrapolated horizontally (constant depth equal to the nearest CPT's values).
  3. Layer matching: layers are matched by soil-type ID. If a layer exists in one CPT but not an adjacent one, it pinches out linearly. The pinch-out is shown visually as the region tapering to zero thickness.
  4. Terrain capping: the uppermost layer at every x is clipped to the terrain surface. No layer can extend above the terrain. If interpolated layer tops exceed terrain elevation (e.g. on a slope face between a crest CPT and a toe CPT), the region polygon follows the terrain.

CPT repositioning

Placed CPTs can be dragged horizontally along the terrain (the y-coordinate tracks the terrain). This re-triggers the interpolation. CPTs can also be deleted (right-click → delete, or select + Delete key), which re-triggers interpolation with the remaining CPTs.

Minimum configuration. The solver requires at least one CPT (providing at least one soil type with c', φ', γ). A model with zero CPTs has no soil properties and cannot be solved. The UI should disable the "Run" button and display a message until at least one CPT is placed.

12.4Phreatic surface drawing

The phreatic surface tool works identically to the terrain drawing tool (§12.2) with these differences:

  1. The phreatic polyline is drawn in a distinct colour (blue, semi-transparent) and dashed style.
  2. It does not require monotonicity in x — the water table can have local dips (e.g. drawdown near a drain). However, it must span the full horizontal extent of the terrain or the solver will treat uncovered zones as dry.
  3. The phreatic surface is constrained to lie at or below the terrain. If a vertex is placed above the terrain, clamp its y to terrainY(x) and show a visual warning. Artesian conditions (phreatic above terrain) are not supported in v1.
  4. The phreatic surface is optional. If not drawn, the solver runs with u = 0 everywhere.

12.5Entry-exit zone definition

For the entry-exit search mode (§4.3), the user defines two zones on the terrain surface.

Drawing mode

  1. User activates the "Entry zone" tool. Click two points on the terrain to define the entry segment (highlighted in green). The segment must lie on the crest/upper portion of the terrain.
  2. User activates the "Exit zone" tool. Click two points on the terrain to define the exit segment (highlighted in red/orange). The segment must lie on the face/toe/lower portion of the terrain.
  3. Constraint: the exit zone must be entirely to the right of (higher x than) the entry zone. If violated, show an error.
  4. The zones are drawn as thick highlighted segments on the terrain polyline, with translucent fill extending slightly below the terrain for visibility.

If the user does not define entry-exit zones, the solver uses the grid-radius search (§4.2) which does not require zones. The UI should offer both search modes: "Auto search (grid)" and "Guided search (entry-exit)" with a toggle or radio button.

The surcharge-zone tool mirrors this same interaction model: activate the tool, click the terrain at the loaded interval start, click again at the interval end, then assign the uniform intensity q. In the current version the zone is a highlighted terrain segment plus a numeric intensity, not a separate free-floating load object.

12.6Vertex editing & snapping

All drawn polylines (terrain, phreatic) and placed markers (CPTs) are editable after creation. The editing model is consistent across all element types.

Selection

  1. Click on a vertex (within a hit-test radius of 8 screen pixels) to select it. Selected vertex shows a larger circle (8 px) with a contrasting fill.
  2. Click on a segment (within 5 px perpendicular distance) to select the parent polyline. The entire polyline highlights.
  3. Click on empty space to deselect.
  4. Tab cycles selection through vertices of the active polyline.

Dragging

  1. Drag a selected vertex to move it. Enforce all constraints during drag:
    • Terrain vertex: x must stay between its left and right neighbours (monotonicity). y is unconstrained.
    • Phreatic vertex: y must stay ≤ terrainY(x). x-monotonicity is not required.
    • CPT marker: drag only in x. y auto-tracks terrain.
  2. Snap to grid during drag if grid-snap is enabled. Show snap indicators (thin guidelines).
  3. Show real-time coordinate readout during drag.

Insert vertex

Double-click on a segment to insert a new vertex at that position. The vertex is added between the two segment endpoints. The polyline is re-sorted. This allows the user to add detail to a terrain profile after initial drawing.

Delete vertex

Select a vertex and press Delete or Backspace. If the resulting polyline would have fewer than 3 vertices (for terrain) or 2 vertices (for phreatic), reject the deletion and show a warning. Terrain cannot be fully deleted this way — use a "Clear terrain" action for that.

12.8Manual region override

In some cases, the linear interpolation between CPTs does not capture the real geology. The user may want to manually override a region boundary or add a region that the CPTs did not detect.

Override polyline tool

  2. Draw a polyline that represents a layer boundary. This polyline replaces the interpolated boundary between the two CPTs it spans.

  2. Assigns a soil type from the material panel (click on the region, then click a soil type in the panel, or use a dropdown).

The solver receives exactly one object: a frozen SlopeModel (§7) plus search configuration. The solver has no knowledge of the canvas, screen coordinates, UI state, or any rendering concept. The contract is:

// ── Solver input: everything the solver needs, nothing more ──

struct SolverInput {
  model: SlopeModel {
    terrain:  Polyline         // world-space vertices
    phreatic: Polyline | null  // world-space vertices, or null if dry
    surfaceLoad: {xStart, xEnd, q} | null
    regions:  SoilRegion[]     // closed polygons + soil type refs
    soilTypes: SoilType[]      // c', φ', γ, γ_sat
  }

  searchMode: "grid" | "entry_exit"

  // for grid mode:
  gridConfig: {
    gridNx, gridNy, nRadii,
    refineNx, refineNy, refineNr
  }

  // for entry-exit mode:
  entryExitConfig: {
    entryZone: {xStart, xEnd},
    exitZone:  {xStart, xEnd},
    nEntry, nExit, nXc
  }

  // shared:
  sliceConfig: {
    nTarget: int,           // default 30
    minDepth: float,        // default 0.5 m
    maxExitAngle: float,    // default 60° in radians
  }
  solverConfig: {
    maxIter: int,           // default 50
    tolerance: float,       // default 0.001
    keepBest: int           // default 10
  }
}

// ── Solver output: everything the UI needs to render results ──

struct SolverOutput {
  searchResult: SearchResult  // as defined in §7
  timing: {
    totalMs: float,
    trialCount: int,
    avgMsPerTrial: float
  }
}

The canvas/UI layer is responsible for converting the visual model into this contract. The solver is responsible for returning SearchResult. There is no coupling beyond this interface. This separation is essential for testability (the solver can be tested with hardcoded SolverInput objects, no canvas needed) and for the Web Worker boundary (the input/output must be serialisable).

14.4Undo/redo & serialisation

Undo/redo

Every model-mutating action pushes the previous SlopeModel state onto an undo stack. The stack has a maximum depth of 50 entries. Ctrl+Z / Cmd+Z pops the stack and restores the previous state. Ctrl+Shift+Z / Cmd+Shift+Z redoes.

Mutating actions that create undo entries: place terrain vertex, finish terrain, move vertex, delete vertex, insert vertex, place CPT, move CPT, delete CPT, place phreatic vertex, finish phreatic, define entry/exit zone, define or move surcharge zone, change surcharge intensity, draw manual region, change soil type parameter, change soil type colour. Pan and zoom do not create undo entries (they are viewport changes, not model changes).

Serialisation (save/load)

The entire SlopeModel plus the viewport state (panX, panY, scale) plus the search configuration plus the last SearchResult (if any) is serialised to JSON. This JSON can be saved to local storage or exported as a file. The schema version is included at the top level for forward compatibility.

  "model": {
